> 评测内容源自 Kilo Code 团队，参考 https://blog.kilo.ai/p/glm-52-vs-kimi-k27-code-which-model

6 月份，Kimi K2.7 Code（后简称 Kimi） 与 GLM 5.2 （后简称 GLM）相继发布。

作为价位接近的两个头部开源权重模型，我们在相同的 Agent 环境中，让他们执行同一个后端开发的任务，实测对比了双方的能力水平。

评测分为 planning 和 building 两个阶段。我们先让两个模型出具架构规划，给方案打分并选出胜者。然后清空环境，让两个模型执行胜出的规划，实现具体的服务。

结论是：**GLM-5.2 和 Kimi K2.7 在编码执行上的表现在伯仲之间，但规划能力有所差距。GLM 的架构方案拿到了 9.0 分，Kimi 则为 8.1 分。**

## 为什么规划能力是模型分水岭

当前的编码 Agent 在执行层面已经做得足够好。只要给到一份详细的方案文档，它们实现的效果大差不差，真正难的地方在于方案设计与规划。

核心在于如何从一份粗糙的需求和模糊的场景里梳理出系统全貌，预判各种隐藏问题，然后整理成一份清晰明确的落地指南。

如同诸葛亮火烧博望坡一役，把谁在何时何地，看到什么信号作何反应安排得明明白白。这份顶层规划足够严谨周密，即使执行者并非关张赵，大概率也能让曹仁灰头土脸。

为了考验规划能力，我们特意设计了一道看似常规、实则埋雷的测试任务。

## 灰度发布的隐蔽陷阱

任务要求模型从零设计并实现一个特性开关服务，且必须具备灰度发布控制能力。比如一个商城要上线新的结账流，要求先推给 5% 的用户公测，随后能随时平滑扩量到 25%，直至最终全量。

这道题里有个坑点：灰度状态必须保持连贯。如果一个用户命中了首批 20% 的公测名单，当测试比例扩大到 40% 时，他必须依然留在名单里，功能不能得而复失。

同时，考题限制了暴力解法：系统不能为了记住这些用户，就把几百万人的分组结果全存进数据库里。

## Planning 阶段：GLM 判断更强

两个模型都避开了直接存数据库的笨办法，同时采用了哈希分桶算法（将 User ID 计算出一串固定数字的哈希值，然后按 100 取模映射到 0 到 100 的固定区间。这样系统只需判断该用户的哈希映射值是否小于当前的灰度百分比即可。）

为了评估除分桶算法之外的其余能力，我们用了一个加权评分表。评分维度在写提示词时就已按需求逐条固定，并在看到任何模型输出前锁定，避免“先看答案再改判分标准”的后验偏置。评测结果如下：

核心差距主要体现在边缘 case 的预判上。

一个典型 case 是在“查询不存在的开关”时，为了不让这些无效查询压垮数据库，GLM 在设计中加上了缓存空结果（负面缓存）的机制，但它也同时指出了缓存失效隐患：如果之后真正创建了这个空开关，那就得立刻清空之前的缓存。

Kimi 给出的方案则完全没有提及这个 case。

在灰度分桶算法上，GLM 考虑了一个关键场景：同一位用户在 Staging 和 Prod 两个环境里，都应该落在同一个灰度批次。因此，它在计算哈希值时剔除了环境因子。

而 Kimi 则没有做到这一点。

在存储 API Key 时，Kimi 直接选用了 bcrypt（业界存储用户密码的标准方案）。GLM 则选用了普通的 SHA-256，并详细解释了打破常规的原因：密码之所以需要慢哈希，是因为人类设置的密码太简单，容易被彩虹表猜中；但 API Key 是机器生成的随机长字符串，根本不存在被暴力枚举的风险。如果在这种高频鉴权请求上套用缓慢的 bcrypt，除了白白消耗服务器算力外，没有任何安全收益。

Kimi 给出的规划内容更长，甚至提前写好了一些伪代码片段，这当然也有一定价值。

但方案规划的核心在于把系统里最棘手的问题提前识别出来并给出合理的解决方案。这一点 GLM 明显更胜一筹。

## Building 阶段：规划决定执行质量

进入编码阶段，我们在一个空目录里放入了 GLM 胜出的 `plan.md`，然后给每个模型都分配了全新、干净的终端会话。Kimi 也许要按照 GLM 给出的规划来执行。

随后我们用一套提前写好的打分脚本，对成品进行了 15 项黑盒测试。

测试内容以业务排雷为主，包括：失效 Key 是否被正确拒绝？重启服务后状态会不会漂移？修改阈值后能不能绕开缓存立刻生效？落盘后的密钥文件是否保证不可读？

结果显示：**GLM 通关了全部 15 项，Kimi 过了 14 项。**

对于关键的灰度发版一致性问题，我们用同一批 200 个真实的 User ID 去请求这两个服务，并将灰度开启比例调到 35%。

结果是：两个模型实现的后端服务都算出了 77 名测试用户，这些用户不仅名额一致，并且具体到每个人的 ID 也都分毫不差。

即使是两个完全不同的开源模型，只要有了优质的方案规划，它们写出来的微服务底层行为依然是高度吻合的。

在具体的实现层面，GLM 写了更多的代码，测试覆盖得也更全面，并且接住了 Kimi 未覆盖到的 case：在刚创建完开关的瞬间主动抹除之前的负面缓存。

可以说 GLM 不仅是个好建筑师，还是个心思缜密的泥瓦匠。

## 总结

**在架构规划上，GLM-5.2 是更强的模型。** 它对于各种边缘 case 的考虑更为细致周密。

**在代码编写上，双方质量接近。**两个模型在同一个技术方案下，给出的实现基本一致。

当下这批开源权重模型已经完全有能力胜任真实业务的规划与代码落地。对于开发者而言，它们不仅是大幅降低了使用成本，而且做到了很高的可用性保障，不会出现闭源巨头们的 API 断供问题。

期待国产模型变得越来越好！
