> TL;DR：Claude Code 每次请求都会携带系统提示词、工具说明和历史对话等大量上下文。pxpipe 在本地把其中适合转换的高密度文本渲染成 PNG，以较低的图片 Token 成本交给模型读取。一组编码任务实测显示，输入 Token 用量减少了 53%，代价是模型可能误读图片中的精确字符。

## 请求成本是如何产生的

输入量主要来自随请求反复发送的上下文。除了刚输入的指令，还包括：

- 系统提示词和工具文档
- 较早的对话记录
- 已读取的源代码和配置文件
- 终端命令及其输出
- 工具调用结果

上下文会随会话增长，其中不少内容还会重复出现。系统提示词、工具说明和旧对话可能连续发送很多轮。新指令只有几句话时，这些重复内容反而会占掉大部分输入 Token。

代码、JSON 和日志尤其明显。它们字符密集，经过分词后会占用大量文本 Token。

## pxpipe 如何降低请求成本

文本和图片的 Token 算法不同。文本按分词结果计数，图片 Token 主要按图片尺寸计算，与图中文字的多少无关。

它把密集文本排进固定尺寸的图片。以一段约 **48,000 个字符**的系统提示词为例，直接发送可能消耗约 **25,000 个文本 Token**；渲染成高密度图片后，可能只需约 **2,700 个图片 Token**。

pxpipe 对真实 Claude Code 请求的测量显示，在这些请求中，高密度内容平均每个图片 Token 可以承载约 **3.1 个字符**，文本形式则接近每个 Token **1 个字符**。内容越密集，转成图片通常越省 Token。

pxpipe 不压缩文本本身，而是直接把文字图片发送给模型，由模型通过视觉能力读取内容。

## 运行机制

pxpipe 是一个本地代理，位于 Claude Code 和模型接口之间。一次请求会经过以下步骤：

1. Claude Code 将请求发给本地 pxpipe 代理。
2. pxpipe 分析请求中的各类上下文。
3. 代理估算每段内容以文本和图片发送时各需多少 Token。
4. 符合条件的文本被排版并渲染成 PNG。
5. 处理后的请求被转发给模型。
6. 模型读取文本和图片，并以普通文本返回结果。

pxpipe 只处理发往模型的请求，不修改模型返回的内容。Claude Code 的流式输出、工具调用和操作方式都不受影响。

## 哪些内容会被转换

图片并非始终更便宜。短文本和稀疏内容转成图片后，消耗的 Token 可能比原始文本更多。pxpipe 会先估算两种方式的用量，确认能节省 Token 后才转换。

代码、日志、大型文件和终端输出通常适合转成图片。普通文字密度低，直接发送往往更省。pxpipe 结合数百次真实请求的测量结果定义了一个转换判断阈值。

内容在上下文中的位置也会影响转换方式：

- 最近几轮对话保留为文本，保证当前任务信息清晰可读。
- 较早且已经折叠的对话可以转换成图片。
- 静态系统提示词和工具文档适合转换。
- 大段文件内容和命令输出会根据估算结果决定是否转换。

这样可以减少误读对当前任务的影响，但无法彻底消除图片识别错误。

## 安装和使用

pxpipe 可以通过 `npx` 直接启动，不需要全局安装：

```bash
npx pxpipe-proxy
```

代理默认监听本机的 `47821` 端口。启动 Claude Code 时，将 Anthropic API 的基础地址指向该端口：

```bash
ANTHROPIC_BASE_URL=http://127.0.0.1:47821 claude
```

设置完成后，Claude Code 的请求会自动经过 pxpipe。浏览器访问 `http://127.0.0.1:47821` 可以打开 Dashboard。它会列出原始文本、渲染后的图片、估算节省量和当前模型，方便核对代理具体改了什么。

如果需要完全关闭图片转换，可以把 `PXPIPE_MODELS` 设置为 `off`：

```bash
PXPIPE_MODELS=off npx pxpipe-proxy
```

此时 pxpipe 只转发请求，不修改其中的内容。

## 模型配置

pxpipe 是否可靠，取决于模型读取高密度文字图片的能力。不同模型的准确率差异很大，只有 `PXPIPE_MODELS` 允许列表中的模型才会启用图片转换。

Fable 5 是主要适配的模型，默认启用。在 pxpipe 的测试中，它读取图片内容时表现稳定。

Opus 4.8 默认关闭。在同一组测试中，它误读了约 7% 的图片内容。需要启用时，必须手动加入允许列表：

```bash
PXPIPE_MODELS=claude-fable-5,claude-opus-4-8 npx pxpipe-proxy
```

其他模型会收到未经修改的文本请求。部分较早的 GPT 模型读取图片文字的效果较差，也不适合默认开启。模型列表可以通过环境变量修改，也可以在 Dashboard 中调整。

## 精确字符串风险

模型能看懂图片里的代码和说明，不代表它能认对每个字符。ID、哈希、密钥和访问令牌只要错一个字符，就可能变成另一个值。更麻烦的是，这类错误通常不会触发异常，模型会直接按错误内容继续处理。

在 12 位十六进制字符串的测试中，即使表现较好的模型也无法保证每次都读对。要求逐字节一致的内容不应依赖图片上下文。

任务涉及大量精确字符串时，可以使用允许列表之外的模型，让请求保持纯文本形式。例如：

```bash
CLAUDE_CODE_SUBAGENT_MODEL=claude-sonnet-4-6
```

也可以在 Agent 的 frontmatter 中指定透传模型。不过，这种配置只能让特定任务使用纯文本，不能自动找出并保护请求里的所有精确值。

## 其他限制

渲染 PNG 需要时间。请求越大，需要转换的内容越多，发送前的等待越明显。这段预处理会增加延迟，但不会改变模型端的推理过程。

输入 Token 减少 53%，也不等于最终账单一定少 53%。实际费用还受模型价格、缓存、输出 Token 和订阅方案影响。

## 实测效果

pxpipe 公布的两条大型请求记录中，输入 Token 分别减少了约 59% 和 70%。另一组以高密度编码为主的独立测试中，Dashboard 记录的降幅为 53%。

这些数字不是固定收益。代码、日志和重复上下文越多，pxpipe 通常越有用；短对话和普通文字可能很少触发转换。文件大小、会话长度、文字密度和模型配置都会影响结果。

判断它是否值得长期使用，不能只看 Token。还要检查任务结果是否稳定，以及图片里的精确字符串有没有被读错。

## 使用结论

如果 Claude Code 会话很长，里面又有大量代码、日志和工具输出，pxpipe 值得测试。接入后无需改变原有用法，转换过程也能在 Dashboard 中逐项检查。

它不适合要求字节级准确的任务，未经验证的模型也不应直接开启图片转换。建议先用自己的工作负载跑一段时间，确认节省量和任务质量都能接受，再决定是否长期启用。
