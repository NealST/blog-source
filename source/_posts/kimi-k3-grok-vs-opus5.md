## 测试题：用 Go 写一个可验证的嵌入式 KV

我们制定了一份 `kvd` 的开发规格，这是一个用 Go 语言编写的嵌入式键值存储系统。它就像是个轻量版的 Redis，只有一个独立的二进制程序，通过 TCP 提供一套精简的文本协议，只不过数据必须持久化到磁盘上。

我们之所以选它作为考题，是因为它提出的所有要求都可以被明确验证：当你强制杀掉进程时，数据要么还在，要么就丢了，没有任何含糊的余地。具体的规格要求包括：

- 单个 Go 二进制程序，通过 TCP 提供类 Redis 的文本协议，支持读写、删除、批处理、统计和数据压缩清理（compaction）
- 持久化铁律：服务端必须在数据真正刷入磁盘后才能返回确认响应，并且任何已确认的写入，都必须能扛住随时发生的 `kill -9` 强杀
- 批处理原子性：最多包含 1,000 条指令的批处理操作必须同生共死。即便进程在中途崩溃，这些操作也要么全部生效，要么全不生效
- 崩溃恢复：在重启过程中，服务端需要通过校验和（checksum）识别出日志末尾写到一半的损坏记录并将其丢弃，且绝不能丢掉任何前面的完好数据
- 性能与规模：支持 1,000,000 个键，能够处理大于内存容量的数据集，并且崩溃后的恢复时间不能超过 60 秒
- 纯标准库：仅允许使用 Go 标准库，禁止使用任何第三方存储引擎

开发这种系统，真正的难点都在于如何处理各种故障倒下的场景。系统既要能从崩溃中恢复，安全地扔掉写了一半的坏记录而不伤及前面的好数据，还要保证批处理在中途中断时依然能保持原子性。这也是我们的测试重点瞄准的核心目标。

## 两阶段流程

两套方案都在相同的 agent 环境下运行，并且使用了完全相同的提示词。在推理强度的设置上：Claude Opus 5 在两个阶段都开启了 `xhigh`，Kimi K3 设定为 `max`，Grok 4.5 则设定为 `high`。

**第一阶段：规划。** 我们明确告知负责规划的模型：你写出的方案将被直接交给另一位工程师去实现，对方无法看到原始的开发需求，也不能向你提问。因此，这份方案包含所有的细节——从精确的通信协议到每一条持久化铁律都得交代清楚。在规划阶段只要漏掉任何一个需求，负责写代码的模型就永远不可能知道它的存在。

**第二阶段：实现。** 我们起了一个全新的会话，并且只提供前一阶段生成的方案文件。Claude Opus 5 负责实现它自己出的方案，而 Grok 4.5 则去实现 Kimi K3 规划的方案。两边的实现端都绝对没看过初始的规格要求。

采用这种严格的交接机制，能让我们精准地把每一个 Bug 追溯到对应的源头。如果从需求规格到技术方案的过程中漏掉了东西，那就是规划器的责任；如果方案本身没问题，而是写出来的代码出了错，那问题就出在实现端。

## 评分方式

在模型正式动手之前，我们预先编写了一套 Python 测试框架。这套框架基于规格说明中的通信协议，能对任何实现了该协议的服务端进行验证和评分。测试共包含 6 组 65 项检查，分别涵盖：协议一致性、崩溃注入环境下的持久化、批处理原子性、数据压缩清理（compaction）、数据一致性以及规模测试。

持久化测试的逻辑非常严苛：测试框架会记录发出的每一次写入请求，只要收到服务端的回复，就将其标记为“已确认”。随后，框架会在某个随机时刻使用 `kill -9` 强杀掉服务端进程，待重启之后，逐字节地核对每一条“已确认”的记录是否仍然完好无缺。在持续并发写入的环境下，这样的断电测试每个组会重复执行十次。

测试框架搞定了所有能被自动化验证的指标。对于剩下的部分，我们则人工通读两边的代码库，重点评估测试用例的质量、文档的准确度以及代码的整洁度，仔细排查那些自动化测试无法触及的隐蔽缺陷。

## 规划阶段

Claude Opus 5 产出的方案篇幅是 Kimi K3 的两倍多，并且多出来的部分并非凑字数，而是实打实的干货。里面包含了详尽的决策表、明确标出 `fsync` 必须在哪里执行的对照明细，甚至还对在各个崩溃点下该如何进行恢复做了分步的沙盘推演。相比之下，Kimi K3 的方案更加精简，但也同样涵盖了必备的持久化规则、通信协议以及批处理原子性设计。

在生成规划方案时，Claude Opus 5 还意外触发了一次配置上限。

Agent 默认的单步输出限制是 32,000 个 Token，而开启了 `xhigh` 推理强度的 Opus 5，是我们见过的头一个在单次推理思考中就把额度跑爆的模型。

这就导致我们在最初的几轮测试里，流程跑完却连一个字儿的方案都没能保存下来。

随后，我们将上限彻底放宽到模型支持的 128,000 Token 并重新运行。在最终成功那次里，仅其中一个单步操作就输出了近 37,000 个 Token。

所以，只看表面的 Token 单价其实会掩盖真实的成本差距：因为 Opus 5 在推理思考阶段产生的 Token 数量远远多于另外两个模型，而这部分隐形成本同样是按“输出”价格来计费的。

这两份方案也都存在一些瑕疵，并且这些瑕疵直接影响了后续的具体实现：

- 面对协议中的一个边缘边界场景——如何处理超大批次时，两边的规划器竟然犯了完全相同的错误，这点下文会展开。
- Kimi K3 的数据压缩清理（compaction）设计存在逻辑漏洞：如果在执行压缩期间删除了某个键，系统重启后这个键就有可能出现“死而复生”的幽灵状态。因为在底层，这个键的压缩副本被保留了下来，但它对应的删除记录却没能保存住。

## 实现阶段

Claude Opus 5 耗费了 76 分钟，不仅完成了基础开发，还顺手写了一套能覆盖 14 种不同崩溃场景的测试用例，并在完整的百万键规模下进行了基准测试。而 Grok 4.5 仅用了短短 11 分钟就完成了任务，代码量大约只有前者的四分之一，它的测试用例主要覆盖了常规的正常路径，外加一次简单的崩溃测试。

![](https://substackcdn.com/image/fetch/$s_!BSko!,w_1456,c_limit,f_webp,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F53bda61c-58f9-4fec-9b05-eec2549ee2a0_1864x810.png)

值得一提的是，Grok 4.5 并没有盲目照抄原方案里的压缩漏洞。它主动修改了设计，将数据压缩清理与写入操作改为串行执行，并在压缩完成后彻底清理掉所有旧的数据文件，从而成功补上了 Kimi K3 方案里留下的两处缺口。反观 Claude Opus 5，则表现得过于“老实”，原封不动地把自己方案里的那个错误给写进了代码里。

## 工作方式的风格差异

两套方案在工作风格上大相径庭。Claude Opus 5 习惯于反复打磨自己的产出。它的规划会话总共执行了 49 步，其中有 23 步都在修改已经写好的方案。到了实现阶段更是跑了足足 150 步，其中包含了 79 条 shell 命令，完全沉浸在“构建代码、运行自测、根据报错修复问题”的循环迭代中。

相比之下，Kimi K3 和 Grok 4.5 的处理方式更像是一气呵成的“单次成案”。Kimi K3 仅用 7 步就生成了方案然后停手；Grok 4.5 也只用了 22 步，就把代码、测试用例和 README 文档一口气写完并宣布收工。

Claude Opus 5 多出来的时间和资金成本，很大一部分就消耗在了这种自我打磨的循环里，这也很好地解释了为何它最终交付的测试和文档会显得深刻细致得多。

当然，如果通过特定的提示词加以引导，那套低成本组合大概率也能进入类似的自验证循环。但我们这次并没有这么干，我们主要想评估它们在“默认状态”下的工作行为。

## 崩溃测试：打平

自动化检查结果完全一致。

![](https://substackcdn.com/image/fetch/$s_!Sd-M!,w_1456,c_limit,f_webp,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F5166188b-4ca0-4313-858f-94dbdc94f601_1864x1258.png)

两边都没有丢失任何一条已确认写入。百万键规模的数据集，恢复时间也都控制在 1.5 秒以内。

即使在数据文件末尾额外追加了垃圾内容，两边也都没有让它影响到前面的有效数据。代码层面两边都是先把数据刷到磁盘，再返回确认；同时，记录里带有校验和，能识别出有没有写到一半；而且一批操作会作为一条完整记录写入，所以不会出现只写进去一半的情况。

## 两边都存在一个相同的缺陷

规格规定批次最多 1,000 条操作。超过这个上限时，服务端必须直接报错拒绝，而且一条超限操作都不能执行。问题在于，服务端虽然拒绝了这个超大批次，却没有把超限操作一并扔掉，它们还留在连接里，下一次读取时会被当成新的独立命令来执行。

我们用脚本复现了这个问题：先发送一个包含 1,001 条操作的超大批次，再观察服务端后续行为。结果是，Claude Opus 5 在返回“拒绝”后，仍然把这 1,001 条操作全部执行了；而 Grok 4.5 在连接关闭前又执行了 2 条。这里的“2 条”是脚本实测结果，不是按“超过上限 1 条”推导出来的理论值。也就是说，客户端看到“已拒绝”并不等于“没有写入”，数据库里仍可能留下本不该提交的数据。

根因在方案里。Claude Opus 5 的方案明确写了这种错误行为：批次过大时，连接保持打开，但不消费后续操作。Kimi K3 的方案没有说明这些待处理操作该怎么处理。两边的实现都照着各自的方案写，于是独立做出了同一个缺陷。

两边自己的测试套件都没有覆盖这种情况，因为它们都没发过“超大批次加附带操作体”的用例，所以自测都能通过。问题之所以被我们抓出来，是因为测试框架是按规格写的，而不是照着模型自己的测试来验收。

## 多花的大约 30 美元买到了什么

最终分差 5 分，全部来自代码评审，而不是自动化正确性。

**测试。** Claude Opus 5 的套件在 14 个时点杀进程，还会截断文件、翻转比特来验证恢复，并对协议解析器做模糊测试。Grok 4.5 只有一次崩溃测试，从未在批处理或压缩过程中杀进程。

**文档。** Claude Opus 5 的 README 有 746 行，逐行对照代码后仍然成立。Grok 4.5 的 README 覆盖了必写主题，但声称了代码里并不存在的 macOS `fsync` 行为。

**整洁度。** Grok 4.5 留下了一些边想边写的注释和死代码。Claude Opus 5 的代码库干净得多。

**残余缺陷。** 除了共同的批次缺陷，Grok 4.5 的压缩错误路径里还有一处狭窄窗口，可能留下过期数据文件。Claude Opus 5 的实现里没有找到同类问题。

也有一项反过来：恢复 512MB 数据集后，Claude Opus 5 占用 428MB 内存，Grok 4.5 为 223MB。原因是 Opus 5 恢复路径里的内存估算偏大，不是设计方向问题。两边都把值存在磁盘上，而不是全部放进内存。

## 结论

在正确性上，这次测试分不出胜负。两边一致性得分相同，崩溃测试结果相同，还带上了同一个关键缺陷，且缺陷都来自规划阶段。就「实现」这件事而言，Grok 4.5 在这次任务上没有输给 Claude Opus 5。

若看长期要维护的代码库，Claude Opus 5 更强：失败路径测试更全，文档与代码一致，也没有死代码和残留注释。代码要进长期协作仓库时，这几分差距有实际意义。

不考虑成本时，默认仍会选 Claude Opus 5，整体交付更好。若价差只有两三倍，为更好的交付多付钱也合理。但这回是 25 倍，就很难盲目推荐贵的那条路径——除非是关键任务，或多出来的分数能明确对上多出来的成本。那大约 30 美元买到的东西，事后也最好补：再花大约 1 美元让 Grok 4.5 加深测试并校对 README，常规 Code Review 也能清掉整洁度问题。崩溃安全是事后补不回来的部分，而低成本组合在这方面没有让步。

这套组合还有提升空间。团队尚未实测，但若调整提示词，推动 Kimi K3 与 Grok 4.5 进入 Opus 5 那种默认的迭代复查循环，交付质量很可能还会提高。想复现同样的分工，Kilo 支持按模式指定模型：Plan 模式用 Kimi K3，Code 模式用 Grok 4.5。

还有两点让低成本结果超出预期。第一，Grok 4.5 主动修掉了规划器的压缩漏洞，说明便宜的实现端并不只会机械照做。第二，Kimi K3 权重已公开，随着更多服务商托管，价格还有下行空间——今年每个开源权重发布后，都出现过同样走势。

最有用的发现仍是那个共同缺陷：价格差很多的两个模型独立规划，却犯了同一个错，且两边自测都通过。缺陷之所以暴露，是因为对照规格写的测试框架在模型动手前就已经定好。这种外部测试的成本，跟你选哪家模型无关。
