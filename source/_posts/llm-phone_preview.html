全选下方内容 → 复制 → 粘贴到公众号编辑器（此行不会被复制）

太长不看（TL;DR）： 核心工作流可以归纳为三步：使用 Unsloth 进行全参微调 -> 结合 TorchAO 做量化感知训练 -> 导出为 ExecuTorch 支持的 .pte 格式部署到手机。在 iPhone 15 Pro 或 Android 旗舰机上，Qwen3-0.6B 的推理速度能达到约 40 tokens/s。它的最大优势是完全离线运行，数据始终保留在本地设备。

···

几个核心概念：

  • Unsloth：一个专门针对大语言模型（LLM）优化的加速训练库。通过手写底层 Triton 算子与优化内存管理，它能把微调模型的显存占用和时间成本砍掉大半。在这套流程里，它负责帮我们用极低的资源跑完模型的全参微调。
  • TorchAO（Torch Architecture Optimization）：PyTorch 生态内原生的模型优化工具箱，专门做量化、稀疏化这些“瘦身”工作。这里我们主要利用它，在训练阶段让模型提前适应极低精度（INT4），从而保证压制后的模型不会变成“人工智障”。
  • ExecuTorch：Meta 内部的大一统端侧机器学习底座。Instagram 里照片的一键抠图功能、Messenger 里的端到端本地语音识别，底层其实都是它在调度算力。开源后，它打通了 Apple、高通、ARM 等不同架构硬件，甚至能无缝跑在 Quest 3（Meta 旗下那款对实时算力和低延迟要求极其苛刻的混合现实头显）上。对于开发者来说，直接调用 ExecuTorch 就能免费使用过去只有头部大厂才具备的端侧部署基建。

整个部署分为两个阶段：首先通过脚本导出兼容的模型文件，然后在 iOS 和 Android 环境中分别跑通部署流程。

第一阶段：准备并导出模型

这里以 Qwen3-0.6B 为例。为了省去本地配置环境的麻烦，推荐直接使用官方配置好的 Colab 笔记本。

首先安装必要依赖：

bash
pip install --upgrade unsloth unsloth_zoo
pip install torchao==0.14.0 executorch pytorch_tokenizers

在加载模型时，有一个不甚显眼但极为关键的参数 qat_scheme="phone-deployment"：

python
from unsloth import FastLanguageModel
import torch

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Qwen3-0.6B",
    max_seq_length = 1024,
    full_finetuning = True,
    qat_scheme = "phone-deployment", # 画个重点，就是这个
)

为什么需要这个参数？ 它开启了 QAT（Quantization Aware Training，量化感知训练）。常规的后量化（PTQ）直接将训练好的模型从 16-bit 压缩到 INT4，往往会导致明显的精度损失。而 QAT 会在训练期间插入伪量化层（Fake Quantization），在维持浮点计算的同时，强迫模型提前适应 INT4 的精度截断。这样做的好处是，最终打包出来的量化模型，其表现更接近未经压缩的原始版本。

全参微调结束后，我们需要将模型转交给 ExecuTorch，打包出移动端最终使用的 .pte 文件：

bash
# 1. 转换权重命名格式，使其适配 ExecuTorch
python -m executorch.examples.models.qwen3.convert_weights "phone_model" pytorch_model_converted.bin

# 2. 获取预设的 0.6B 配置参数
curl -L -o 0.6B_config.json https://raw.githubusercontent.com/pytorch/executorch/main/examples/models/qwen3/config/0_6b_config.json

# 3. 导出 .pte 模型包
python -m executorch.examples.models.llama.export_llama \
    --model "qwen3_0_6b" \
    --checkpoint pytorch_model_converted.bin \
    --params 0.6B_config.json \
    --output_name qwen3_0.6B_model.pte \
    -kv --use_sdpa_with_kv_cache -X --xnnpack-extended-ops \
    --max_context_length 1024 --max_seq_length 128 --dtype fp32 \
    --metadata '{"get_bos_id":199999, "get_eos_ids":[200020,199999]}'

执行完毕后，当前目录下生成的 qwen3_0.6B_model.pte（大约 472MB）就是最终要在手机上加载的模型产物。

部署路线 A：iOS 环境

将模型部署进 iPhone 需要 Xcode 开发环境。宿主机需要 macOS 系统及 Xcode 15 以上版本。如果要跑在真机上，还必须拥有付费的 Apple 开发者账号。

1. 配置 macOS 编译环境

从 Mac App Store 下载 Xcode。安装好之后，在终端校验并安装命令行工具：

bash
# 校验安装是否成功
xcode-select -p

# 安装命令行工具
xcode-select --install
sudo xcodebuild -license accept

敲黑板：首次启动 Xcode 时，系统会弹出额外组件的安装提示，这个时候直接点安装，不要跳过。如果提示选 platform，勾选 iOS 18 即可，用来后续启动模拟器。

2. 真机的开发者权限

ExecuTorch 的运行需要提升应用的内存上限（Increased Memory Limit Capability）。苹果对这项系统级权限限制很严格，开发者必须有付费的 Apple Developer Program 账号进行签名，普通的免费个人账号在运行时会直接遭遇闪退。

准备部署真机的朋友，请在 Xcode → Settings → Accounts 中登录相应的开发者账号。

3. 获取测试应用

为避免从头编写 UI 交互，可以直接拉取 Meta 提供的示例 App 源码：

bash
curl -L https://github.com/meta-pytorch/executorch-examples/archive/main.tar.gz | \
  tar -xz --strip-components=2 executorch-examples-main/llm/apple

解压后，双击 apple/etLLM.xcodeproj 在 Xcode 中打开该项目。你可以忽略项目加载初期的非关键警告，在顶部设备栏选择 iPhone 16 Pro 等模拟器目标，点击编译运行（▶️），此时模拟器中会安装一个缺失模型的基础应用。

4. 在模拟器中加载模型

在模拟器里挂载模型文件需要手动操作目录：

  1. 先在 Xcode 中点击停止键，关闭以编译模式运行的 App。
  2. 切换回虚拟 iPhone，打开自带的 Files 应用，在 On My iPhone 路径下新建一个文件夹，命名为 Qwen3test。
  3. 打开 Mac 终端，查找这个虚拟容器在真机上的物理路径：
bash
find ~/Library/Developer/CoreSimulator/Devices/ -type d -iname "*Qwen3test*"

拿到实体路径后，将导出的模型文件与分词器拷贝过去：

bash
cp tokenizer.json /你的查询结果路径/Qwen3test/tokenizer.json
cp qwen3_0.6B_model.pte /你的查询结果路径/Qwen3test/qwen3_model.pte

随后从模拟器桌面再次启动 etLLM，在应用内选择加载这两个文件即可体验。

5. 真机部署方法

用数据线将 iPhone 连接至 Mac，并在手机端同意“信任此电脑”。然后在 Xcode 的项目导航栏选中 etLLM 靶标：

  • 进入 Signing & Capabilities 页面。
  • 勾选 Automatically manage signing。
  • 在 Team 一栏选中已付费的开发者账号。
  • 修改 Bundle Identifier（换成一个不冲突的域名，如 com.你的名字.etLLM），以规避大部分代码签名错误。

此处有一个关键步骤：在界面左上角点击 + Capability，搜索并添加 Increased Memory Limit。如果不加此权限，应用在运行时会因极速消耗内存而崩溃退出。

在顶部目标栏选中已连接的真机，点击编译运行。首次安装通常会触发不受信开发者的拦截警告：

  • 解锁 iPhone，进入 设置 → 隐私与安全 → 开发者模式 并开启。
  • 手机重启后，返回 Xcode 重新构建安装。

接下来是传输模型文件：打开 macOS 的 Finder（访达），从侧边栏进入你的 iPhone 设备选项，切换至顶部的 Files 标签。找到 etLLM 图标后，将大约半个 G 的 .pte 模型库以及 .json 分词器文件拖放进去，等待同步完毕。

最后，在手机上打开 etLLM App，加载文件后便能开始离线对话。

部署路线 B：Android 环境

Android 的部署体验相对轻量得多，不需要安装厚重的 Android Studio 开发套件，只需在 Bash 终端里准备好基础的交叉编译工具链，最后通过 ADB 推送产物即可。

环境依赖：必须锁定 Java 17

编译这套 Android 源码时，常见的阻碍是系统 Java 版本过新。如果使用目前常见的 Java 21 等高版本，Gradle 在解析依赖时会抛出异常中断执行。系统必须配置并切换至 Java 17。

检查当前 Java 版本：

bash
java -version

若非 17，可通过以下方式进行安装与切换（以 Ubuntu/Debian 为例）：

bash
sudo apt install openjdk-17-jdk
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export PATH=$JAVA_HOME/bin:$PATH

Step 1 & 2：配置 Android 命令行工具集

无需图形界面，直接在终端下载 Command Line Tools 构建最小化环境：

bash
mkdir -p ~/android-sdk/cmdline-tools
cd ~/android-sdk

# 获取命令行工具压缩包
wget https://dl.google.com/android/repository/commandlinetools-linux-11076708_latest.zip
unzip commandlinetools-linux-*.zip -d cmdline-tools

# 重构目录树，这是 sdkmanager 稳定运行的硬性要求：
mv cmdline-tools/cmdline-tools cmdline-tools/latest

将以下环境变量写入 shell 配置文件（~/.bashrc 或 ~/.zshrc）：

bash
export ANDROID_HOME=$HOME/android-sdk
export PATH=$ANDROID_HOME/cmdline-tools/latest/bin:$PATH
export PATH=$ANDROID_HOME/platform-tools:$PATH

执行 source 使其生效。

Step 3：部署指定版本的 NDK

当前编译框架对环境参数有严格要求：NDK 需要精确匹配到 25.0.8775105，平台对应 API 34。

bash
yes | sdkmanager --licenses
sdkmanager "platforms;android-34" "platform-tools" "build-tools;34.0.0" "ndk;25.0.8775105"

export ANDROID_NDK=$ANDROID_HOME/ndk/25.0.8775105

Step 4 & Step 5：拉取源码与编译预置

bash
cd ~
git clone https://github.com/meta-pytorch/executorch-examples.git
cd executorch-examples

在这里提前给出两个常见编译错误的解决办法（碰到再执行即可）：

  • 若报错 SDK Location not found，强制指引 SDK 路径： bash echo "sdk.dir=$HOME/android-sdk" > llm/android/LlamaDemo/local.properties
  • 若因 API 弃用报 cannot find symbol，替换问题代码： bash sed -i 's/e.getDetailedError()/e.getMessage()/g' \ llm/android/LlamaDemo/app/src/main/java/com/example/executorchllamademo/MainActivity.java

Step 6 & 7：编译与安装

进入工程目录，再次确保 Java 版本绑定无误后执行构建：

bash
cd llm/android/LlamaDemo
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
./gradlew :app:assembleDebug

编译成功后，产物输出在 app/build/outputs/apk/debug/app-debug.apk。

确认手机连接状态并开启了 USB 调试，运行命令进行全量推送安装：

bash
adb install -r app/build/outputs/apk/debug/app-debug.apk

B. 直接传文件（替代方案）

如果你是在远程 VM 上构建或者手口没线，也可以把 app-debug.apk 传到手机端文件管理器，点击授予未知来源权限后直接安装。

Step 8：推送模型文件至 Android 系统

普通的系统文件管理器受限于权限很难访问对应的 App 预留目录，我们可以通过 ADB 手动切入并推送临时文件：

bash
# 验证设备连接
adb devices

执行完这条命令后，手机上通常会弹出一个 USB 调试的授权确认对话框，要点击“允许”，否则后续的传输会被直接拒绝。

设备连接就绪后，接下来就得在手机文件系统中创建一个专属目录，用来存放生成的 .pte 模型文件与 tokenizer.json 分词器。

bash
# 建立隔离路径并分配读取权限
adb shell mkdir -p /data/local/tmp/llama
adb shell chmod 777 /data/local/tmp/llama
adb shell ls -l /data/local/tmp/llama  # 检查目录生成状态

# 推送模型和分词器（耗时较长，请耐心等待）
adb push <本地 tokenizer.json 路径> /data/local/tmp/llama
adb push <本地 qwen3_0.6B_model.pte 路径> /data/local/tmp/llama

应用层操作：

  1. 打开手机上的 Executorch Llama Demo，点击右上角齿轮进入设置

  2. 点 Model 旁边的下拉框，选中刚刚推送过的 .pte （如果没有文件名出现，说明之前的 adb push 流程断录失效了，需要重传）

  3. 用同样的方式选中 tokenizer 分词器

  4. 确认模型种类归属（这里是 Qwen3）

  5. 点击 Load Model，静待片刻缓冲

  6. 底部浮现 successfully loaded model 返回界面，端侧部署即宣告成功。

排错速查

  • 构建意外终止？ 首查 java -version。底层库存在强耦合，切勿在此混用其他版本的 JDK/JRE，死咬 17 版本。
  • App 闪退或模型加载失败？ 请回退去检查 .pte 和 tokenizer 是否准确选中。如果是直接闪退，检查自己的 .pte 是不是并未对 ExecuTorch 单独兼容导出。

支持的衍生模型扩展

这条工作流并不仅限于服务 Qwen3-0.6B。经过转换脚本的通用适配，它能够吃下当下主流开源模型的多数构架：

  • Qwen 3 家族：0.6B、4B、32B 等版本。
  • Gemma 3 家族：270M、4B、27B 等参数量级。
  • Llama 3 家族：Llama 3.1 8B、Llama 3.3 70B Instruct 等。
  • 基于相同架构微调出的 Qwen 2.5 或 Phi-4 等小型版本同样可行。

官方的 Colab 环境中已提供对应不同预设版本的现成笔记本，照着对应环境运行并替换下载直链即可。

写在最后

这套部署架构对于开发者最直接的吸引力有两点：无网络依赖的零延迟和数据完全在本地带来的隐私安全。此外，端侧大模型还可以节省云端算力。但目前主要受限于内存限制，硬件结构的兼容性等问题，高参数的大模型目前还是没法支持。

但在一些比较特殊的场景，比如金融和政企这种高度隐私安全的重地，编写一些内部材料或者利用 AI 查询私有知识，端侧大模型会更有用武之地。
