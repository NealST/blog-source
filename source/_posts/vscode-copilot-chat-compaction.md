大模型的上下文窗口有限，当一个 Agent 会话达到临界点时，VS Code Copilot Chat 会触发“压缩（Compaction）”机制：总结并折叠旧的记录，同时原样保留最近的对话内容。

为了弄清楚这层黑盒究竟是怎么运作的，我翻了一遍它的底层源码。

> ps：独立的 `vscode-copilot-chat` 仓库已于 2026 年 5 月停止更新并被归档。目前 Agent 的全部核心逻辑都在主库 `microsoft/vscode` 的 `extensions/copilot/` 目录下。本文的追踪基于该目录的最新代码。

### 核心基建：@vscode/prompt-tsx

`@vscode/prompt-tsx` 是一个自带 Token 预算感知能力的 Prompt 渲染器。它抛弃了传统的“直接把字符串硬塞进 `messages` 数组”的做法。开发者用类似写 react 页面的方式通过一段段嵌套的 TSX 组件拼装出整个 Prompt 骨架，然后渲染器会把整个骨架翻译成发给大模型的对话数组（`ChatMessage[]`），过程中会顺手算清所有的 Token 数额，并在空间超载前自动完成文本裁剪。

先看一眼精简后的 Agent 真实 Prompt 结构（`agentPrompt.tsx`）：

```tsx
return <>
  {baseInstructions}
  <AgentConversationHistory flexGrow={1} priority={700} promptContext={ctx} />
  <AgentUserMessage    flexGrow={2} priority={900} {...userMessageProps} />
  <ChatToolCalls       flexGrow={2} priority={899} toolCallRounds={ctx.toolCallRounds}
                       truncateAt={maxToolResultLength} />
</>;
```

裁剪的取舍由每个元素上的两个标识属性来决定：

*   **`priority`（优先级）**：当渲染树突破了模型最大 Token 预算时，渲染器从优先级最低的节点开始丢弃。在这里，当前用户输入（`900`）和最新的工具调用（`899`）比早期的历史记录（`700`）权重要高，同级节点排在前面的优先被剪切。
*   **`flexGrow`（空间伸缩比）**：大模型的 Token 池就像一个固定容量的行李箱。当拥有较高优先级的基础内容装进去后，如果行李箱还有剩余空间，带有 `flexGrow` 属性的元素就可以按照设定的数字比例来扩充自己，填满这部分空隙。在 Copilot 的配置里，用户直接输入的提问和底层工具执行的结果最为重要，它们的伸缩系数为 2（`flexGrow={2}`），这保证了它们会优先吃掉多余的空间，而对话历史的系数仅为 1（`flexGrow={1}`），只能捡剩下的边角料。

这种“自我管理容量”的设计，让整个额度分配过程有条不紊。因为每一个组件节点在执行其生命周期方法 `render(state, sizing)` 时，渲染器都会传入一个包含实际限制的参数 `PromptSizing`。这个参数不只有当前的 `tokenBudget`，还提供了一个异步的 `countTokens()` 测量函数，使每个组件在装载时都有了感知水位的能力，一旦体积过大就能主动“瘦身”。

上述示例的 `<ChatToolCalls>` 组件中，有一个 `truncateAt` 属性指定了 `maxToolResultLength`，其核心作用就是利用函数估算工具输出，如果输出结果远超阈值界点，就直接剔除冗长部分。

当上下文窗口膨胀到已经无法容纳优先级最高的内容时，渲染器会抛出 `BudgetExceededError` 异常，Agent 捕捉到异常后，改为用总结概括的方式压缩上下文。

### 压缩任务的触发

除了用户手动调用的 `/compact` 命令外，Copilot 内置有两套自动触发策略。

| 触发路径 | 触发条件 | 是否默认开启 |
| :--- | :--- | :---: |
| **前台兜底** | 渲染抛出 `BudgetExceededError`（发生硬溢出） | ✅ 是 |
| **后台并行** | 本轮渲染完成后，由 `backgroundSummarizer` 的后台状态机先做占比检查；若超线，再由它异步发起压缩任务 | ✅ 是 |

系统界定“容量阈值”时，除了模型参数给定的上限值，还会兼顾用户设置的 `effectiveMaxTokens`。这个配置的规则是：当值为 `0` 到 `1` 之间的小数（比如 `0.8`）时，系统会将其当作全局比例系数，当上下文占比到 80% 就该触发压缩；当值为 `≥100` 的整数（比如 `4000`），系统会将其当作上下文总和的硬性 Token 数额边界。但如果两者都不是（比如 `50`），系统会直接抛出运行错误。

从机制分工上看，Copilot 是把“兜底修复”和“常态预热”拆开做的：前台兜底只负责处理硬超限这种兜不住的极端情况，后台并行则负责平时先把压缩任务悄悄做掉。

这种分工的原因是前台兜底是一个串行流程：先尝试渲染，发现上下文超限后抛出 `BudgetExceededError`，再临时去做一次历史总结，最后拿总结结果重新渲染第二遍，体验上会有较为明显的卡顿感。

为了最大化享受到模型上下文的“提示词缓存（Prompt Cache）”红利，后台触发机制加入了三个很精细的操作：

1. **热缓存约束与随机扰动界标（Jitter）**，当模型缓存处于“温热”状态，比如刚经历过工具调用，这种状态下，压缩任务跑起来更快也更便宜，触发时机可以提早一些，可以到 80% 的红线阈值就执行。同时，为了避免阈值总落在同一个点，用户体感上在相同位置反复出现停顿，系统引入了 `0.78` 到 `0.82` 的一个轻微浮动界标。在没有模型缓存的冷启动场景下，压缩成本更高执行更慢，Agent 会等到 90% 再启动压缩。
2. **同源复刻，不动声色**。跑后台压缩任务时，它并没有去给 AI 丢个带“请总结一下上述内容”的新任务。那会当场击穿 Anthropic 模型视角的缓存追踪。相反，代码直接复写了前序主流程发出的整套对话列阵状态，仅在最末端掺入一层极易被忽略的后台隐藏触发符，等待模型跑完再逆向去解包带有 `<summary>` 字段的回包。
3. **安全抛弃下限**。只要后台费劲周折抓回了产物总结，却发现在此空档期内上下文配比滑落了——比如用户顺手在页面更迭配置挑了个长窗版模型，这包热乎的文档便会被就手丢进垃圾桶停用，一切按原逻辑继续执行。

### 内部的切分逻辑

Copilot 并不会简单粗暴地要求 LLM 对整个对话文件重头再来做一个全盘摘要，实质上这是一套递推式的叠加重制流。

1. **反切定位**：代码逆序回溯并坚决留存最首近几个对话轮次元数据记录。这就确保模型无需靠猜，自然地直接顺上业务思路。
2. **踢出触发溢出的轮次**：假设你在当前一轮挂起一长串巨无霸工具调用请求，这套把原本窗口填满的触发源步骤将排除在本次合并目标外。
3. **寻找存档点**：在后退检索路线上，如摸到上一个既成事实的压缩档（带有 `.summary` 标志）立停。历史的摘要总被叠进这一级，而不是重复翻译远古细节。
4. **生成压缩包**：唤起模型接口归纳产物。
5. **原位替换**：封好的 `<conversation-summary>` 伪装块直接覆盖掉原内容，并保留它过关到后续。

此外系统中工具返回的文本结果在进窗前皆被粗暴腰斩至上限。模型最大 Token 的 50% 额度留用，系统抽取 40% 的首部和 60% 的尾部合并，截断其中部的内容。

### 强制执行的工作交接表

用来压缩文本的调用接口坚决不使用阉割版的小型模型执行。它绑定当前会话用户指定的原始模型型号，强行将 `temperature` 设定为零并要求以流式开启作答步骤。

此时的系统前置提示词极其蛮横，明确要求模型起手以 `<analysis>` 做思考反馈，在其后提供涵盖下述八条结构清单的 `<summary>` 数据：

1. 会话概览（明确全盘目标、当前状态关联和根本意图转变轨迹）。
2. 技术基底（涉及关键架构和套用栈版本）。
3. 文件库现状（精准标记哪些在动、为啥动以及对应的关键逻辑变更指向）。
4. 卡点解决方案（记录遭遇过的 Bug、出路和保留用上下文环境）。
5. 推进表（何为已经结项、何为有待补修和已证明可靠的状态判定）。
6. 最后定帧状态（刚刚这双眼盯着的那行代码在哪）。
7. 行动指纹（最终命令和最后收底结果与触发总结前快照对齐）。
8. 后续指引（待办单以及眼皮下面第一步起手操作）。

若环境无法负荷此要求强硬度，程序则默认回落剥离这套结构体属性调用的极简“Simple mode”。

### 遗留面包屑：索引留存在缓存里，细节留给本地盘

没有任何花里胡哨的技术能抹消压缩本身的破坏性。真刀真枪跑出的堆栈排错文本总归有需要再次捞出的一天。

Copilot 利用一段极其巧妙地通配指令挂在重置文档尾部以确保找回门路：

“如果你面临需要读取压缩前具体细节的麻烦（如查找确切原生代码片段、错误截断信息或是找回原曾提供的生成内容等情况），务必用 `readFile` 工具直接去挖掘本地存档 `transcriptPath` 的全部原生会话源内容获取支撑。”

这个纯文本面包屑被彻底“焊死”。一旦执行后未来轮次它就变成了在模型视角里固化的只读块片段，它天然吃透各类服务方在底层设置的主动静态提示词缓存预存规则。而极耗定额的原文档文本，一直被压放在开发电脑的安全硬盘转录包里，等到模型明确认定需要精细追因才触发单波加载。这是很经典的渐进式信息暴露应用打法：在寸土寸金的上下文环境内铺下低价索引，将重量级的请求查询推迟剥离到刚需点再行动。

### 踩过坑的模型特定绕行规则

接入不同模型存在差异。当处理这块特定内容时，底座代码暴露出不同厂家模型间的细微体感分化：

*   **Opus 家族**：系统专给它贴上一张“切勿激活工具只能打字输出文本”的操作罚单口令。
*   **Anthropic 且附带思维链（Thinking）**：系统会妥善保留它的最后一组思考数据（Thinking block），并将其重新挂载到生成摘要后的第一个动作思考区域前。
*   **Anthropic 且支持网络搜索（tool_search）**：在发送浓缩请求前，程序必须客户端手动刮除历史里的 `tool_search` 对应问答配对轮次，否则 Anthropic 直接报 400 失败。
*   **Gemini**：如果上一波工具裁切刚好使其剩下了干秃的函数唤醒 `function_call` 词元而缺少返回值，会连报 400 失败。在丢还上去前必定彻底搜捕拦截移除该结构。
*   **GPT-4.1**：在紧跟总结数据的结尾追补一句“请继续保持”的提示。

### 最后

顺便提一下，如果你关注过配置选项，可能还记得以前有个针对这块压缩的开关分支控制（`chat.conversationCompaction.usePrismCompaction` 和针对它的模型黑白名单过滤 `prismModelFilter`）。目前的架构下，默认全由 Agent 主力端点自行完成一切压缩调度。

比较同样面向自动编码 Agent 问题的 Claude Code 后台管理设计，不同产品的风格各有千秋。Claude Code 的 `/compact` 也是折叠历史块。而 Copilot 暴露在代码背后的底层哲学指明了实现可靠工作流循环的要点：**在进行非对称的强制压缩前尽最大可能依赖优先级裁剪边缘旁支**；并**在剥离细节记忆后送出一把通过工具链直接读取溯源数据的安全钥匙**。这就是它在有限长窗内玩出花活的秘密。
