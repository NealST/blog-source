作为 VS Code Copilot 的 Pro+ 会员和高频用户，我感受最爽的就是其丝滑的上下文管理体验，使用过程中几乎感觉不到上下文压缩带来的停顿等待。

我很好奇它是怎么做到这点的。

于是，我去读了其 chat 实现的源码，发现了一堆令人叹服的工程细节。我认为 Copilot 的上下文管理是可以作为 Agent 产品的范例来效仿的。

> ps：独立的 `vscode-copilot-chat` 仓库已于 2026 年 5 月停止更新并被归档。目前 Agent 的全部核心逻辑都在主库 `microsoft/vscode` 的 `extensions/copilot/` 目录下，本文拆解源于这份最新代码实现。

## 核心基建：@vscode/prompt-tsx

在讲具体的压缩机制前，需要先介绍 `@vscode/prompt-tsx`，它是一个自带 Token 预算感知能力的 Prompt 渲染器。与传统的“直接拼接字符串传入 `messages` 数组”的做法不同。Copilot 通过 TSX 组件拼装出完整的 Prompt 骨架（PromptElement），然后渲染器负责将其扁平化，再转换为发送给大模型的对话数组（`ChatMessage[]`），并在这一过程中自动适配给定的 Token 预算。

先瞅一眼精简后的 Agent 真实 Prompt 结构（`agentPrompt.tsx`）：

```tsx
return <>
  {baseInstructions}
  <AgentConversationHistory flexGrow={1} priority={700} promptContext={ctx} />
  <AgentUserMessage    flexGrow={2} priority={900} {...userMessageProps} />
  <ChatToolCalls       flexGrow={2} priority={899} toolCallRounds={ctx.toolCallRounds}
                       truncateAt={maxToolResultLength} />
</>;
```

裁剪的取舍由每个元素上的两个属性控制：

*   **`priority`（优先级）**：当渲染树超出预算时，渲染器会最先丢弃优先级最低的内容。在这里，当前用户输入（`900`）和最新的工具调用（`899`）优先级高于历史记录（`700`），而历史记录的优先级又高于 Copilot 模版指令。如果是同一优先级的节点，则按代码声明顺序依次裁剪。
*   **`flexGrow`（空间伸缩比）**：控制剩余预算的分配方式。带有 `flexGrow` 的元素会延后到所有非动态的次要节点都处理完毕后，再进行体积测量。此时系统会将剩余的所有 Token 额度打包，按 `flexGrow` 的比例切分并灌入。在这个例子中，剩余额度会分成 5 份：用户输入（`flexGrow={2}`）与最新工具调用（`flexGrow={2}`）会优先各自瓜分 40% 的主力空间，剩下的 20% 再分配给历史对话（`flexGrow={1}`）来填充。

除了底层的优先级调度，`@vscode/prompt-tsx` 还提供了几个控制配额的属性：
- `TokenLimit`：为特定子树施加 Token 硬上限。
- `PrioritizedList`：为子元素列表按序分配递减（或递增）的优先级，通过这种精确的打分排序，确保了越旧的对话轮次被优先丢弃。
- `TextChunk`：应对大段文本，尽可能多地保留预算内能塞下的内容。

每一个组件节点在执行生命周期方法 `render(state, sizing)` 时，都会收到一个包含 `tokenBudget` 和异步 `countTokens()` 函数的 `PromptSizing` 参数，节点可以自主测量体积并执行内部约束，上述例子中，通过传入 `truncateAt={maxToolResultLength}` ，就能允许工具输出自我设限（比如截取不超过窗口 50% 额度）。

当上下文容量超出上限时，`prompt-tsx` 会抛出 `BudgetExceededError` 异常，此时Copilot从普通的节点裁断策略切换到上下文压缩流程。

## 调度协作：压缩链路的内部执行顺序

如果在逻辑上只依靠捕获 `BudgetExceededError` 来触发压缩，会有严重的体验问题：前台捕获异常属于串行阻塞流程。Copilot需要尝试渲染、遭遇报错、临时发起摘要任务然后等待模型返回，最后重新渲染，这会阻断用户的提问交互。

Copilot 在对话轮次中会交替执行上述渲染器的裁剪策略和后台的并行压缩任务。当用户提交问题后，引擎内部的执行链路如下：

1. **预检与挂载（Pre-Render）**：在执行正式渲染之前，Copilot首先检查后台压缩器（`backgroundSummarizer`）。若后台在此前的空闲时段已经完成了摘要生成（状态为 `Completed`），且当前上下文占比达到了应用阈值（`applyMinRatio`），Copilot立即提取摘要并原位替换长对话历史。该操作为单纯的内存状态同步，无额外请求开销。
2. **常态渲染与异常协同（Render & Fallback）**：提取结果后（或无可提取产物时），Copilot按组件优先级正式渲染 Prompt。若经计算并未超限，流程顺利结束；如果依然抛出 `BudgetExceededError`，则进入前后台协同的排险分支：
   * 异步挂起：若后台任务处于 `InProgress`（执行中）状态，Copilot挂起当前线程（`await waitForCompletion`）以等待后台作业完毕，并复用其结果，避免重复发起大模型请求。
   * 强制串行：若后台任务处于 `Idle`（空闲）状态，表明之前的容量尚未触及后台警戒线，此时的超额是由当前过大的输入（如单次粘贴海量代码）瞬间击穿上限导致的。Copilot被迫调用 `renderWithSummarization` 触发兜底：阻塞主流程，强制模型先完成历史摘要生成，释放空间后再处理当前提问。
   * 降级渲染：若强制压缩后仍抛出 `BudgetExceededError`，Copilot记录失败状态，调用 `renderWithoutSummarization` 取消摘要任务，直接切除超额历史进行渲染。
3. **后置评估与预热分发（Post-Render）**：当本轮提问全部响应发出后，Copilot会重新评估最终的 Token 占用率。如发觉整体容量逼近警戒位，且当前不存在进行中的压缩任务，Copilot会再次派发异步任务（`_startBackgroundSummarization`），并在客户端闲置时静默执行，为下一轮对话准备好可用的压缩快照。

## 阈值判定与 Prompt Cache 利用

在判断阈值时，Copilot 不仅会参考模型的预设上限，还会解析用户配置中的 `effectiveMaxTokens` 参数，参数设置的规则为：
* `0` 到 `1` 之间的浮点数（如 `0.8`）：按比例换算为容量上限。
* `≥100` 的整数（如 `4000`）：作为绝对的 Token 数量硬上限。
* 非法数值（如 `50`）：直接报错中断。

此外，对于代码搜索等高产出工具，系统会先扣除工具配额，再将剩余预算乘以 `0.9`。强制预留 10% 的缓冲空间，专门用来吸收不受控的超长输出，防止运行时 Token 溢出报错。

为了最大化利用提示词缓存减少摘要请求消耗，Copilot 后台还做了一些非常精细的操作：

1. **热温分类与界标扰动（Jitter）**：当关联上下文处于缓存“温热态”时，单次压缩成本极低，上下文窗口占比阈值设定为 `80%`，同时，为了避免固定阈值造成的局部卡顿体感，底层策略加入了 `0.78` 至 `0.82` 间的界标扰动。在冷启动（如挂机后唤醒）状态下，无缓存可用，阈值会推迟到 `90%` 再触发压缩。
2. **全量克隆与静默提取**：单独发起摘要请求会改变 Prompt 结构，导致提示词缓存失效。为最大化利用缓存，Copilot在后台压缩时会全量克隆当前的对话上下文，仅在末尾追加一条生成摘要的指令。由于前置文本保持不变，大模型能直接命中已有缓存以降低计算开销。最后，Copilot从返回结果中剥离并保存 `<summary>` 标签内容即可。
3. **容量滑落废弃**：摘要生成是异步执行，如果中间用户切换至上下文窗口更大的模型，原有的占比则会滑落。为了避免无效的摘要替换，Copilot 在应用摘要前会执行二次校验：若当前容量占比已跌至 `0.65` 以下，则丢弃摘要结果，沿用原始会话内容。

## 内部的切分逻辑

Copilot 并非简单地把整段对话扔给 LLM 去生成一个全盘摘要，它执行的是一套“近端保留 + 远端滚动折叠”的增量压缩逻辑。

1. **保留最近上下文**：Copilot 会逆向回溯会话历史，原样保留最近的几轮对话，以确保用户可以延续当前的对话讨论。
2. **剔除溢出轮次**：当发生多轮连续的工具调用时，Copilot 会将最终导致溢出的那次调用从摘要范围中剔除，确保只对超载前的、完整的安全历史进行压缩。
3. **命中已有存档点**：在逆向遍历历史记录时，Copilot 一旦读取到带有 `.summary` 标记的过往摘要节点，就会立即中止回溯。全新的压缩任务会直接提取这份旧摘要，将其与新产生的对话文本一并交给模型，最终融合成一份最新摘要，避免每次压缩都必须从头开始，节省计算开销。
4. **原位替换**：当模型生成并返回压缩产物后，Copilot 将其放进一个虚拟的 `<conversation-summary>` 对话节点中，覆盖掉原会话内容。这个新节点将作为稳定的元数据驻留，继续衔接后续的对话轮次。

此外，在保留最近上下文的机制设计下，Copilot 必须防范另一种极端情况：某个刚调用的读取工具可能直接返回了十万行的报错日志，对于这种 case，底层配置对工具输出施加了严格的大小限制：任何单一工具的返回文本，其体积不可超过模型总 Token 额度的 50%。

当出现长文本超限时，渲染器会直接剔除长文本的中间区块，仅按比例留存开头的 40% 与末尾的 60%。这种策略既能有效保留报错的异常堆栈与关键信息，又避免了庞大工具输出瞬间阻断上下文窗口的问题。

## 摘要的本质：高密度的状态快照

当大量的历史对话被折叠后，Agent 极易出现“失忆”或上下文断层。因此，这里的“摘要”并不是简单的几句话概括，而是Copilot 要求模型把当前的任务目标、代码改动记录、抛过的异常以及接下来的计划等具体细节完整记录下来，生成一份可随时恢复工作记忆的**状态快照**。

为了保证这份快照足够精准，Copilot在生成摘要时会直接沿用当前交互的模型，不会为了省钱偷偷降级到小模型。此外，Copilot 还会把 `temperature` 锁死为 `0` 以榨取最高的确定性，并且不会关闭流式响应。

在默认模式下，Copilot 还做了一个非常巧妙的参数设定：在把完整的工具定义传给模型的同时，额外附加了 `tool_choice: 'none'` 以禁用工具调用。这样既能保证模型能看懂工具语义，知道过去做了什么，又能避免其擅自调用新工具，先专注把总结工作干完。

执行压缩时，模型必须先在 `<analysis>` 标签中利用思维链（CoT）推理现状，随后在 `<summary>` 标签内雷打不动地交出这 8 个维度的现场数据：

1. **会话概述**：当前任务的核心目标、背景上下文以及用户意图的演进阶段。
2. **技术底座**：开发涉及的核心架构、框架与设计模式。
3. **代码库演变**：精准标记变动的文件目录及其变更缘由与核心逻辑状态。
4. **问题排解**：遇到的报错信息、对应的解决方案与调试线索。
5. **进度跟踪**：已完成、待处理以及已验证稳定的任务进度。
6. **当前焦点**：触发压缩前，Copilot 最后停留的具体代码或操作。
7. **行为快照**：近期下发的终端命令以及执行的工具调用反馈。
8. **后续计划**：未决的待办清单与恢复状态后所需执行的首要指令。

这种详尽的结构化压缩内容能让 Agent 在后续对话中迅速找回工作状态。

但部分模型未必能完美遵循这种格式要求，如果执行失败，Copilot 会自动降级到极简模式：不强制数据结构，仅做最简单的文字概括。

## 会话面包屑：上下文留索引，本地存明细

压缩是有损的。历史对话一旦被折叠，就会丢失一些原生细节。

但在后续排错中，模型往往还需要回头查阅具体的代码片段或报错日志。

因此，Copilot 会在摘要最后附上一段固定的提示，给模型指明查阅原始记录的路径：“如果你需要读取压缩前的确切细节（比如原生代码片段、报错信息或过去的输出等），请使用 `readFile` 工具直接读取本地归档文件 `transcriptPath`。”

这段提示文本只在生成摘要时写入一次，在后续对话中会原样复用。

完整的原生对话记录存放于本地硬盘，摘要仅作为轻量索引。模型只有在需要确切细节时，才会调用工具去读取本地文件。这种“按需加载”的设计，最大程度节约了宝贵的上下文空间。

## 针对特定模型的兼容处理

不同模型的 API 存在行为差异，Copilot 在底层代码中增加了以下特定兼容逻辑：

*   **Opus 系列**：额外追加一段约束指令，明确要求模型“禁止调用工具，仅输出文本”。
*   **Anthropic（开启 Thinking 时）**：Copilot会保留最后一次的“思考过程”，待摘要生成完毕后，重新插入到新一轮对话的起始位置以保持推理连贯。
*   **Anthropic（调用 tool_search 时）**：Anthropic 接口会严格校验历史工具记录的一致性。由于摘要请求中通常不再声明 `tool_search` 这一特殊工具，客户端必须在发请求前主动剔除这部分记录，避免导致校验失败抛出 HTTP 400 错误
*   **Gemini**：如果此前的上下文裁剪导致某些 `function_call` 丢失了配套的返回结果，Gemini 同样会回抛 HTTP 400。客户端会在发送请求前主动清理这些失效的孤立节点。
*   **GPT-4.1**：渲染摘要后，会在末尾追加“请继续”相关的提示词以维持对话状态。
*   **提示词缓存**：生成的摘要结果只会写入一次，并在随后的对话轮次中直接复用，最大化模型的缓存命中率。
*   **PreCompact 钩子机制**：在压缩上下文前 Copilot 会执行该钩子函数，通常主要用于日志和转录的本地写入。钩子为非阻塞性，即使报错也不会中断主压缩任务。

## 相关配置项

VS Code 为上述压缩流程提供了以下设置项：

*   `chat.summarizeAgentConversationHistory.enabled`：压缩机制总开关（默认开启），统一控制前台与后台的压缩行为。
*   `chat.advanced.summarizeAgentConversationHistoryThreshold`：触发压缩的上下文占比阈值。
*   `chat.advanced.agentHistorySummarizationMode`：指定摘要的生成模式（`auto`、`full` 或 `simple`）。
*   `chat.conversationCompaction.usePrismCompaction`：是否启用 Prism 通道执行压缩（实验性）。
*   `chat.conversationCompaction.prismModelFilter`：配合上述开关使用，指定只有特定主模型才触发 Prism 通道。

ps: Prism 是一个用于降低算力消耗的轻量级模型路由。默认情况下，摘要由当前交互的主模型（如 GPT-4o）生成以维系缓存上下文；开启此选项后，摘要任务会被转交给速度更快、成本更低的小模型独立处理。

## 总结

VS Code Copilot 之所以能带来丝滑的压缩体验，在于其构建了一套多层级的上下文调度系统。

纵观其完整工作流，这套架构有三个关键设计：

1. **渲染层的弹性降级**：依靠 `@vscode/prompt-tsx` 的优先级机制，在本地渲染阶段优先剥离次要节点，最大程度推迟调用模型进行有损压缩的时间点。
2. **调度层的异步掩盖**：确立“后台为主、前台兜底”的双轨机制。将耗时的摘要任务前置到用户的阅读间隙中静默执行，利用异步任务把等待耗时吃掉，避免阻塞后续提问。
3. **存储层的冷热分离**：将历史对话提炼为高密度的状态热快照，再通过只读提示词引导模型去本地硬盘按需查阅原始冷归档。配合提示词缓存优化，在响应速度与信息完整度之间实现了平衡。

在模型窗口依然存在硬性约束的当下，单纯拼接 Prompt 已经走到尽头。Copilot 这套融合了组件化思想、并发调度与缓存治理的架构，我认为堪称 Agent 上下文管理的范本。
