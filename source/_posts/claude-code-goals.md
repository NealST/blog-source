Claude Code 的默认机制是在完成单轮任务后主动暂停并等待用户的下一步指令。但在涉及跨多文件迁移或测试套件修复等长期（Long-running）的 Agentic 编码任务中，这种交互模式会暴露出显著的效率瓶颈：开发者必须在终端前频繁手动输入“继续”以推进流程。

于是 `/goal` 命令应运而生（Claude Code 2026 年 5 月 11 日发布的版本 2.1.138 中开始支持）。

开发者只需定义明确的最终完成条件，系统会引入独立的评估模型（默认调用 Haiku）来审核历史交互链路，并驱动 Claude 自主推进任务，一旦判定条件满足即终止执行。

ps: 评估模型完全受限于已形成的对话记录，并不具备独立触发工具、运行命令或检索文件的越权能力。

## 评估流转机制

启用 `/goal` 后，系统在每次任务轮次（Turn）末尾触发评估链路。

在 Agent 完成文件查阅、代码修改或命令调用的完整序列后，评估模型将拉取全局操作日志，并与设定的 `/goal` 终态条件进行拟合。

鉴于评估模型秉持“零工具权限”的设计，条件设定需满足一个核心准则：

**条件必须声明具备确切衡量标准的操作终态，而非抽象的过程描述。**

范例对比：

`/goal all tests in test/auth pass and the lint step is clean`。该指令驱动 Agent 循环执行测试、排查异常及修正代码，直至评估模型在 stdout 截获到测试用例全数通过且 Lint 告警归零的标识。由于底层工具输出在流水线记录中一览无余且支撑机器校验，这个条件设定就具有很高的可操作性。

反观 `/goal the app is production-ready` 则属无效的条件定义。所谓“生产就绪”是高度主观且缺乏量化标尺的概念，不存在可直接映射的 CLI 运行结果。评估模型如果无法从日志流内提取事实依据，自然失去校验裁量权。

对于每一次裁决，评估引擎都会附带简短的日志回执，便于开发者追踪 Agent 当前执行焦点。

在终端键入无参数的 `/goal` 即可直观查询已耗用轮次、Token 消耗账单及距今最近的判定驳回依据。

## 编写可验证的条件标准

条件最大负荷限值为 4,000 字符。在工程化应用中，一条优质规范通常闭环四项要素：可量化的阶段终态、显式的核查路径、系统不变量约束（如指定模块不可变更），及可选的断路器防护（如轮次或时限阈值）。

推荐范式：

- `/goal all tests in test/auth pass and the lint step is clean`
- `/goal CHANGELOG.md has an entry for every PR merged this week`
- `/goal every call site of the old API has been migrated and the build succeeds, stop after 20 turns`

上述用例均导向物理可观测的结果。Agent 的操作输出可完成对最终状态的逻辑自证，从而赋予评估引擎坚实的验收基准。

定义的模糊极易诱发两类算力空耗的极端案例：

1. Agent 在修复报错与引入新 bug 的泥淖中陷入死循环，Token 流失严重且偏离主线任务。
2. 触发幻觉陷阱：缺乏具体的验证标的致使评估引擎作出误判，产生“虚假繁荣”。

## 三类宿主执行模式

`/goal` 灵活适配 Claude Code 的三种常态化工作环境：

- **交互模式（Interactive mode）** 为默认宿主环境。用户在当前交互 Shell 中直接定义 `/goal <condition>`，拦截后续输入缓冲，直接开启无干预新轮次。
- **非交互环境（Non-interactive mode）** 依靠附加标志量 `-p` 提权运行，达成单次激活直至收敛的效果：`claude -p "/goal CHANGELOG.md has an entry for every PR merged this week"`
- **远程协作模式（Remote Control mode）** 构建在多用户会话中枢，支撑多人研发团队共享并观测同一个远端 Agent 的调度目标。

三种环境在生命周期内均常驻一个 `/goal active` 守护面板，为开发者透传驻留时间、迭代周转与全盘算力账单。

## 内置工作流对比（/goal vs /loop vs Stop Hooks vs Auto Mode）

Claude Code 底层集成四套自主演进流，对应切割不同粒度的工程场景：

- **`/goal`**：基于模型仲裁的状态机循环，适配导向清晰最终里程碑的关键任务轴：大型重构、全量 API 迁移、核心链路用例修复。
- **`/loop`**：基于时钟周期的心跳轮询调度器（如 5min 节拍）。最佳使用域落在轻量级周期巡检：CI/CD流水线嗅探、GitHub 动态摘要。禁忌将其强绑定用于“完成某段具体代码逻辑”等非线性任务。
- **Stop hooks（钩子断点）**：下沉至全局配置体系。捕获作用域内的执行态，通过挂载外部脚本或强指派二次校验执行确定性审计。具备更高的系统接入自由度，但依赖重度预配置。
- **Auto mode（自动应答模式）**：阉割单步操作的人工放行审批，自身并不驱动会话边界更迭。工程界目前最优解为 “Auto mode + `/goal`” 绑定：既保障微观操作的畅顺度，亦锁定宏观目标的兜底完成率。

## /goal 的边界与局限

若缺乏全局 Token 开销钳制，Agent 理论上会无限制重试直至命题证伪。实操中最稳健的干预措施是在约束条件末尾声明断路器阈值（例：`stop after 20 turns`），或外部强拉起 Ctrl+C 硬中断。

评估闭环对系统日志输出高度敏感，如果 Agent 执行操作但刻意截断 Diff 文本或隐藏 Console，系统验证也就宣告破产。因此设定的首要准则是与显性的日志截面深度绑定。

针对巨石复杂度命题（如“完成登陆鉴权切换至 OAuth、集成多环境隔离用例、全量重写使用文档”）进行“包干式”投递，会导致仲裁逻辑失效和算力剧烈消耗。更成熟的工程方案是将超大型需求拆解为串行的状态转移链路，各个标的节点需独立可证。

由于安全审计机制，`/goal` 严格被隔离在显式授权的物理空间。当管理侧开启全局 `disableAllHooks` 或收缩至 `allowManagedHooksOnly` 安全边界后，相关唤醒通道将强制闭塞。

## 项目接入最佳实践

引入以下基础设施基建能显著提升 Agent 运行的达成率：

1. **项目根目录构建 `CLAUDE.md` 知识库**。固化技术栈选型、架构约束、PR 准入标尺等核心指引。此设计方案是为了强行对齐一个 30+ 轮漫长工作流中的记忆偏差。
2. **挂载拦截器 Hooks 补全实时校验**。通过配置 `PostToolUse` 等生命周期卡点，强制挂钩自动化的 ESLint 或类型推演命令，缩短异常捕获路径，将终态校验下放并转为前置拦截。
3. **强开启自动模式（Auto mode）**。未配置该参数的 `/goal` 会在每一步的文件 IO 请求时被挂起，必须依靠 “Auto Mode” 才是全自动无干预编排的最后一块拼图。

若在边界与条件的拿捏上存在争议，也可通过向 Claude Code 下发生语料请求：

> Write me a `/goal` prompt. Ask me what I'm trying to do first, then keep asking follow-up questions until you can describe 'done' in specific, measurable terms.
> （基于上述目标撰写 `/goal` 提示词。首先追问实施思路，继而提出逐步深入的问题，直至构建出具象且衡量标准的任务闭环终态。）

## 写在最后

`/goal` 命令本质上是把人类做的确认是否执行下一步这个反馈交给了一个单独的评估模型来处理，评估模型的判断依据则是人类定义的验收标准和 agent 上一轮的执行结果。如果两者 match, 那么就终止执行，否则就继续推进执行下一轮。

在实际场景中用好这个功能的关键还是在于怎么拆解一个复杂任务然后针对子任务定义一个好的目标，这里其实可以沿用人类目标制定的 SMART 原则，然后基于该原则跟 AI 一起完成条件定义和描述。

搭配使用 Auto mode + `/goal` 命令后，我日常基本上就是全托管模式了，碎片时间的利用率也大幅提升。如果你有其他使用技巧，欢迎评论区交流。
