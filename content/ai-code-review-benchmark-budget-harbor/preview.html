本文素材来源于 Kilo 技术团队的 Review Testing，原文地址：https://blog.kilo.ai/p/review-testing

我们从零写了一个完整的 React 应用，故意埋了 15 个 Bug，然后交给五个主流 AI 模型做 CR。不提示方向，不透露数量，不引导关注安全或正确性，只给了一个 diff 和一句指令：”Review the uncommitted changes.”

结果：Opus 4.8 找到最多（10/15），但真正出人意料的是第二名 Grok Build 0.1，它和 Sonnet 4.6 并列 9/15，而 Grok 只花了 $0.08（对比 Opus 的 $0.75 几乎可以忽略）。更意外的是，这次测试中最难的 Bug，Grok 给出了最完整的诊断。

Gemini 3.1 Pro 最让人失望，其他四个模型都抓到的 Bug，它完全没有发现。另有四个 Bug，五个模型无一检出。

为什么选预算应用

这个应用叫 Budget Harbor，一个基于 React + TypeScript + Vite 开发的家庭预算管理工具。功能包括追踪账户余额、分类预算、周期性交易、储蓄目标，支持 CSV 导入导出和月末预测。

选它的原因很简单：钱的计算对于准确性要求极高，对就是对，错就是错，没有任何可转圜的余地。

15 个植入 Bug 的分类

植入 Bug 分为六类：

类别 数量 典型例子
React 状态与 Hooks 2 useEffect 缺依赖数组、useMemo 依赖数组漏了搜索词
日期与时间 3 子字符串月份匹配、monthKey 时区漂移、周期性调度差一
余额完整性 3 投影余额重新叠加所有交易、新增被重复计算、删除不回退
预测逻辑 2 周期性交易被数两次、信用卡负债被当可用现金
数据健壮性 3 window.localStorage 在 SSR/测试环境崩溃、JSON 损坏时启动崩溃、CSV split 不处理引号内逗号
财务计算 2 储蓄目标贡献方向反了（加变减）、函数按小数读取 APR 但 UI 传入的是百分比

这些 Bug 不会让代码报错，测试也照样能过。关键是你得懂一个预算应用该怎么算钱，才看得出它是否算错。

五个模型没有一个产生误报，标记出来的问题全部属实。差距在于每个模型挖多深，以及它对哪类 Bug 更敏感。

各模型的强项和盲区在这张表里一目了然。Opus 和 Sonnet 包揽了全部日期 Bug，其他模型在这一类别上几乎没有命中。只有 Grok 和 GPT-5.5 完整拆解了余额矛盾，而 Grok 做到这件事只花了八分钱。预测类 Bug 五个模型均未检出。数字背后，每个模型的推理路径和失误原因差异更大。

各模型表现分析

Claude Opus 4.8：覆盖最广，推理最细

Opus 命中了两个 React Bug、全部三个日期 Bug、以及三个余额 Bug 中的两个。

它还做了一件其他模型没有做的事：打开测试文件，手动把样本交易算了一遍，然后报告说提交的期望值差了整整 200，所以 npm run test 会失败。这不是我们植入的 Bug，具体数字是否准确尚未核实，但这种主动验算的本能，通常只有亲自 review 的人类才有。

它在日期问题上的判断也很精准。getUpcomingRecurring 用 new Date(year, month, day) 构造日期，但 JavaScript 的月份参数从 0 开始计数，应用传入的却是从 1 开始的值。Opus 识别出了这个差一问题，指出用户选五月实际会被排到六月。

Opus 在余额类中漏了一个：deleteTransaction 在删除交易时，不会将已计入 base balance 的金额回退。它分析了新增和导入的逻辑，唯独没有覆盖删除，离完整诊断只差一步。

Grok Build 0.1：最大惊喜

Grok 和 Sonnet 并列 9/15，但花费是五个模型中最低的。而且在余额计算这个所有 Bug 中最难的问题上，它给出了最完整的诊断。

这个 Bug 难在它分布于三个文件中，只有多处同时修改状态才会暴露。Grok 在一次分析中做了完整拆解。

addTransaction 每次新增交易都会直接修改 base balance。deleteTransaction 删除交易时却不会把这笔改动撤销。而 getAccountBalances 在计算投影余额时，用的是 balance + sum(transactions)，相当于在已经改过的数字上又加了一遍。

Grok 把这三个错误追溯到同一个根因，指出了重复计算和数值偏移的问题，并给出了修复思路：用不可变账本推导余额，或采用事件溯源确保 base balance 不被直接修改。

余额之外，Grok 对 React Hooks、数据健壮性、财务计算三个类别也都有覆盖，总计另外命中了六个 Bug。其中 CSV 那条值得单独说：它不只是指出 split(',') 有问题，还给出了正确的修复方案。

Grok 的短板集中在日期计算。它看到了 getUpcomingRecurring 有问题，但关注点落在了伪造的 -next ID 会泄漏到下游，真正的零索引月份偏移反而没有认出来。monthKey 的时区漂移则完全没有注意到。不过丢分也就限于日期这一个类别，其余检出全部准确。

Claude Sonnet 4.6：和 Grok 互补的另一半

Sonnet 也拿到 9/15，但路径和 Grok 完全相反。它命中了全部三个日期 Bug（包括 Grok 漏掉的两个），覆盖了两个 React Bug，另外在数据健壮性、财务计算、余额完整性三个类别上也各有命中。

它离 APR Bug 最近。Sonnet 发现 estimateDebtPayoffMonths 有一条兜底逻辑：当月还款额不够覆盖利息时，函数直接返回 600 个月（即上限值），不做任何提示。Sonnet 认为这是个问题并标记了出来。

但它只看到了表象。真正的根因是 UI 把 APR 以百分比形式（19.99）传入，而函数期望的是小数（0.1999），导致月利息被放大了一百倍，几乎任何还款额都会触发这条兜底。Sonnet 没有追到这一层，不过已经比其他四个模型都近了一步。

余额完整性方面，它只覆盖了一半。它抓到了删除不回退的 Bug，但没有发现投影层在已经改过的 balance 上重新叠加所有交易的问题。而这正是 Grok 和 GPT-5.5 检出的部分。

GPT-5.5：数据流推理强，但漏了基础题

GPT-5.5 也完整解出了余额矛盾，拆解思路和 Grok 一致：新交易被投影算两次，删除永远不回退。余额之外，它对数据健壮性和财务计算类也有广泛覆盖，整体命中 8 个。

但 useEffect 缺依赖数组这个 Grok 和 Gemini 一下子就抓到的基础问题它却漏掉了。三个文件的状态联动能追得清清楚楚，这道最基础的 bug 反而没注意到。

Gemini 3.1 Pro：表现配不上价格

Gemini 的结果令人费解，费用和 Grok 差不多，检出率却不到它的四分之一。只抓到两个植入 Bug：useEffect 依赖数组和 CSV 转义。输出也是五个模型里最短的，而且有限的篇幅里还分了一部分给非植入问题（表单默认日期的时区、依赖版本全写 latest 没有锁定），真正该深挖的植入 Bug 反而只触及了表层。

最不该漏的是储蓄目标那个 Bug。逻辑很简单：handler 名字叫”Add contribution”，里面却在做减法，用户每存一笔钱进度反而倒退。这个 Bug 其他四个模型全部抓到了，唯独 Gemini 没有反应。

五个模型都漏掉的四个 Bug

  1. 预测重复计算周期性交易：forecastEndOfMonthBalance 把本月已记录的周期性账单加了一遍，又把生成的周期性账单加了一遍，房租被数了两次。
  2. 预测把信用卡负债当可用现金：同一个函数把信用卡的负余额加进总额，好像一张刷爆的卡是你能花的钱。
  3. localStorage 裸访问 window：loadBudgetState 直接用 window.localStorage，在任何 SSR 或测试环境都会抛错。三个模型抓到了相关的 JSON 崩溃问题，但没有一个抓到裸 window 访问。
  4. APR 单位错误：estimateDebtPayoffMonths 的利息计算假设 APR 以 0.1999 传入，但 UI 传的是 19.99，算出来的还款期完全失真。

漏网的 Bug 有一个共同特征：单独看代码逻辑没有问题，只有理解这些数字的业务逻辑，才能发现计算是错的。数两次房租是合法的加法运算。把负债加进余额看起来也是正常的求和。但如果结合预算应用的业务意图，就能发现这些计算其实是不符合逻辑的。而对业务意图的理解，恰恰是当前模型的短板。

Claude Sonnet 4.6 60% $0.23 $0.026

通常的预期是”便宜换来低检出”，但实际结果令人意外：Grok 每个 Bug 的成本不到一分钱，而检出率和 Sonnet 并列。

Opus 的覆盖面仍然最广，这里只能说一句“贵有贵的道理”。但有效审查的最低门槛，比预想的低得多。

结论

如果你的变更对正确性要求高、上线前需要一道最严格的审查，Opus 4.8 是当前最稳的选择。覆盖面最广，能跨文件追踪状态联动，而且是五个模型里唯一会自己打开测试文件验算数字的。

如果看性价比，Grok Build 0.1 很实在。$0.08 跑完一次完整审查，检出率并列第二，而且在余额模型这个最难的 Bug 上给出了五个模型里最完整的诊断。

它的盲区是日期计算，如果你的代码依赖时区和周期性调度，配上 Sonnet 4.6 正好互补。两者检出率相同但路径完全相反，而且 Sonnet 离 APR Bug 最近。Grok 加 Sonnet 一起跑会覆盖 11/15，超过任何单个模型。

GPT-5.5 在数据流推理上很不错，它拆余额矛盾的方式和 Grok 一样干净。但不要单独用它，因为它跳过了更便宜的模型都能抓到的基础 React 错误。

Gemini 3.1 Pro 能不能用，得先在自己的代码上试一轮。更便宜的模型都能抓到的功能反转 Bug 它直接略过，单模型审查的靠谱程度，到这里得打个问号。

单个模型是筛子不是判决书，两个互补模型或前沿模型加人工过审，仍然是最稳的策略。但”前沿”和”在最难的 Bug 上最强”不是一回事。要真正理解业务领域的 Bug，目前为止还是得靠人。
