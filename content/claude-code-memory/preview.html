全选下方内容 → 复制 → 粘贴到公众号编辑器（此行不会被复制）

最近给我的 Claude Code 接入了 mem0_search 这个工具，用来当作长期记忆层存储和读取项目的关键历史信息。

但实际用下来，发现这个工具没有很自然地融入工作流，每次我都得手动告知 Agent 帮我搜索一下 xx 项目的历史信息。

这就容易导致两个问题：

第一，当前项目的上下文会丢。比如上周沉淀的一些问题解法，新开会话时仍然得从 0 开始，完全记不住。

第二，跨项目经验很难复用。比如我开发当前的活动页项目时，想问下 Agent 另一个类似活动页中是怎么实现某动画效果的。如果没有自动召回，Claude 就不知道这个问题应该关联另一个项目的历史上下文。

我希望达到的效果是：记忆能在合适的时机自动进入上下文，即 Claude 能自己判断是否需要召回、如何召回，以及召回后怎么使用结果。

问题解法：入口召回，过程补召回，退出时捕获

这套方案把记忆分成两个方向：读和写，核心执行时机依赖于 Claude Code 的 Hook 机制。

读发生在回答之前。SessionStart 让 Claude 在会话开始时先召回当前项目上下文。UserPromptSubmit 让 Claude 在跨项目提问时补充召回。

写发生在会话之后。SessionEnd 不在终端里同步做耗时工作，而是启动一个 detached Python 进程，让它读取 transcript、提取重要信息、去重并写入 Pinecone。

简化后可以这样理解：

  • 进来时，按当前项目召回。
  • 对话中，按用户提到的项目补召回。
  • 离开时，异步提取本次会话的新记忆。

会话开始时，按当前项目召回

SessionStart 会在打开 Claude Code 时触发。这里的 hook 是一个 Bash 脚本，只做一件很简单的事：查看当前目录并注入一条针对该项目的召回指令。

bash
BASENAME=$(basename "$CWD")
# 把 BASENAME 和已知的项目 slug 做匹配，设置 $SLUG...

MSG="[session-context] cwd is project '$SLUG'. Before answering the
first prompt, call mem0_search with query=\"$SLUG\" for past
decisions, preferences, and in-flight work."

jq -nc --arg msg "$MSG" \
  '{hookSpecificOutput: {hookEventName: "SessionStart", additionalContext: $msg}}'

通过 additionalContext 我声明了在回答第一个问题之前，先去搜索当前项目的记忆，这样当这串 JSON 返回给 Claude Code 后，Claude 会在后台默默调用搜索工具，拿到当前项目的历史上下文信息。

即使当前目录不在预设的项目列表里，也有个简单的兜底方案：直接拿文件夹的名字当关键词去搜，搜不到返回空数据也没啥关系。

另外，为了防止脚本意外卡死，我额外加了一道 5 秒的超时限制，实际场景下这种 case 其实蛮少发生。

对话中，按用户提到的项目补召回

使用 UserPromptSubmit，当用户发送消息给 Claude 之前。它会读取 prompt 文本，转成小写，然后扫描里面是否出现了任何已知项目 slug，而且必须是完整单词。

bash
for s in $HUB_SLUGS; do
  if echo "$PROMPT_LC" | grep -qE "(^|[^a-z0-9])$s([^a-z0-9]|$)"; then
    MATCHED="$MATCHED $s"
  fi
done

这个正则里的完整词边界非常关键。没有它，短 slug 会匹配到更长且完全无关的词里，普通提示词也会整天触发召回。有了边界，只有真正提到项目名时才会命中。

如果匹配到某个 slug，hook 就注入同样类型的召回指令：在回答前，先拉取这个项目的上下文。没有匹配到就啥也不加，静默退出。

离开时，异步提取本次会话的新记忆

这里较为麻烦一些，使用 SessionEnd 在会话关闭时完成以下工作：

  • 读取完整会话历史内容（transcript）。
  • 把 transcript 发给 LLM，让它提取真正重要的内容。
  • 对每条内容在向量库中进行去重。
  • 写入留下来的内容。

这个过程通常耗时数秒，不适合放在主流程中完成以避免会话关闭的卡顿感。

所以我的设计里， SessionEnd 这个 hook 仅仅只是启动一个 detached 后台进程，然后立刻返回：

bash
(
  "$PYTHON_BIN" "$SCRIPT_PATH" \
    "$TRANSCRIPT_PATH" "$SESSION_ID" "$HOOK_EVENT" "$CWD" \
    </dev/null > "$LOG_FILE" 2>&1 &
  disown
) >/dev/null 2>&1

提取工作会在终端关闭之后继续运行，不需要当场等待。

三个踩坑点

写入链路比读取链路复杂，其中有三个主要的坑点：并行运行、环境变量继承、提炼去重。

并发踩踏死锁

在一口气关掉三四个 Claude Code 会话的 case 下，如果不加锁，就会出现三四个并行提取任务写同一个向量库的情况。

我的解法是在本地加两层锁。第一层是全局锁，核心是利用 mkdir 命令去创建一个特定的文件夹。在操作系统层面，创建同名文件夹是一个“原子操作”：不管有多小的时间差，最终只会有一个进程创建成功。我设定只有创建成功的那个进程才有资格连接并写入向量库，而其他创建失败的进程都会认为“别人在干活”并直接退出，这样就把并发死锁直接挡在了门外。

第二层则是针对单个会话的“专属锁”。有时候终端关闭时由于进程异常或信号重发，会连续多次触发同一个会话的关闭流程。为了防范这种“抽风”，我引入了类似游戏技能的 120 秒冷却机制：同一个会话结算一次后，两分钟内绝不会再被二次提取。这就从根源上避免了重复执行的问题。

环境变量继承

提取器本身只是一个普通的 Python 脚本，但因为它是被 Claude Code 触发的，作为“子进程”，它会默认继承“父进程”所有的环境变量（比如特定的 API 请求地址 ANTHROPIC_BASE_URL、OAuth token 以及一堆 CLAUDE_CODE_* 变量）。

这就导致了一个非常隐蔽的 Bug：Python 脚本在尝试自己去调用外部 LLM 接口时，会被这些继承来的残留变量“带偏”。它发出的网络请求会被错误地重定向，或是带上错误的认证信息，导致提取器频频报错，误以为自己还在 Claude 的内置环境里。

我的解决方式是“打扫干净屋子再请客”：在真正执行 Python 命令之前，先在终端命令里加上一段 unset，把这些继承来的、带有干扰性的 Claude 专属变量全部剔除。让 Python 脚本在一个完全干净的独立环境中运行。

只保留值得记住的内容

后台脚本接收到完整的会话日志（transcript）后，我将其发给 Gemini 2.5 Flash Lite 进行提炼，并附带一个提取范围指向的 prompt：只提取架构决策及原因、个人开发偏好、Bug 根因，以及当前项目的特定事实，其他统一丢弃。

选择 Flash Lite 是因为它包含在免费额度中，而且单纯的上下文提取其实也用不到 sota 的模型。

经过大模型筛选过滤后，留下来的优质内容会被标准化为一个结构化的 JSON：包含核心的经验事实、它所属的项目作用域，以及具体的分类标签（比如标明这是 decision 还是 learning）。

在最终写入之前，我还会把这段 JSON 文本在向量库中做一轮预搜索。如果发现与库中已有记忆的余弦相似度（cosine similarity）超过了 0.88，就会认为是是重复内容不再写入，避免长期记忆被重复语义稀释。

最后，经历层层筛选留下来的记忆才会被正式写入 Pinecone 向量库。在这个环节我特意设置了 infer=False，强制要求系统按大模型吐出的原文原样存储。核心的提炼总结在 Gemini 那一步已经做得足够完整了，底层的向量库没必要再画蛇添足地进行二次改写。

写在最后

通过这套机制，我完全实现了最初设定的想法，现在 Claude Code 可以自动在合适的时机提取当前项目和跨项目的关键记忆。

整个解法主要建立在对 Claude Code Hook 的充分利用上。很多常规思维定势都把 shell-command hooks 看成是一个单纯写运行脚本的地方，但事实是 注入指令的 hook，往往比直接运行命令的 hook 更有价值。
