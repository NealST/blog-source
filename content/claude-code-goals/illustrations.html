CONDITION DESIGN

好的条件 vs 失败的条件

✗ 模糊命题
/goal the app is production-ready
「生产就绪」无法量化，没有任何命令的输出能证明，评估模型容易陷入死循环或产生幻觉。
/goal refactor the codebase
没有终态、没有约束、没有断路器，等于让 Agent 永远在打转。
✓ 可验证条件
/goal all tests in test/auth pass
and the lint step is clean
最终态可由 stdout 直接观测，Lint 与测试结果都在日志流里清晰可校验。
/goal every call site migrated
and build succeeds, stop after 20 turns
终态明确 + 内置断路器，避免无限制重试与 Token 失控。

AUTONOMY MATRIX

四种自动化机制：各司其职

/GOAL
模型仲裁的状态机循环
跨轮次保持会话活跃，直至评估模型判定收敛。适配迁移、重构、测试修复等具备明确终态的任务。
/LOOP
时钟周期的心跳轮询
按 5min、1h 等节拍重跑同一 prompt。适配 CI 嗅探、动态摘要，不适合「完成某段代码」这类收敛型任务。
STOP HOOKS
配置层的钩子断点
挂载在 settings 中，作用域内每个会话触发。可执行确定性脚本或模型评估，灵活度高但前置配置较重。
AUTO MODE
免确认的自动应答
移除单步工具调用的人工放行，但不驱动新轮次。需与 /goal 绑定才能形成真正的无人值守闭环。

PROJECT SETUP

提升 /goal 达成率的三件套

① CONTEXT
CLAUDE.md 知识库
在项目根目录沉淀架构决策、编码规范与 PR 准入标准，确保 30+ 轮的长程任务记忆一致。
② VALIDATE
PostToolUse Hooks
在每次文件编辑后自动触发 Lint / 类型检查，将异常拦截前置，缩短发现到修复的链路。
③ UNATTENDED
Auto Mode 强开启
移除文件 IO 等单步人工确认。Auto + /goal 的组合，是真正实现无干预编排的最后一块拼图。

SMART PRINCIPLE

用 SMART 原则定义 /goal 条件

S
Specific
具体到模块、文件、命令
M
Measurable
stdout / exit code 可量化
A
Achievable
单轮可推进的合理粒度
R
Relevant
与当前任务紧密相关
T
Time-bound
stop after N turns 断路
关键洞察：把人类的「按回车确认」拆为两件事 —— 人定义验收标准，评估模型负责判定 match。复杂任务拆子任务，逐个用 SMART 描述。
