三家共用的核心运行回路

Computer Use 的定义很直接：LLM/VLM 智能体不再依赖操作系统或网页 API，而是直接通过屏幕感知以及虚拟键鼠，与图形界面（GUI）进行交互。 尽管 OpenAI、Anthropic 和 Google 交付的产品形态各不相同，但它们底层都遵循同一套 “观察-思考-行动”（Observe–Think–Act）回路：

•
观察（Observe）：获取当前屏幕状态，形式通常是一张屏幕截图或结构化的元素树。
•
思考（Think）：多模态模型结合思维链（Chain-of-Thought）或自适应思考机制，规划下一步操作。
•
行动（Act）：输出点击、键入、滚动或拖拽等指令，由客户端执行器在沙箱环境中具体执行。
•
循环（Loop）：重新获取操作后的屏幕状态并重复上述流程，直到任务完成或需要人工介入接管。

整体回路是统一的，但三家的真正差异集中在两个维度上：感知通道（纯像素图像 vs 结构化元素树 vs 混合模式）与行动空间（绝对坐标系 vs 元素引用句柄）。后续探讨的所有技术细节，本质上都对应着这两个维度的取舍与实现。

OpenAI：从 Operator 到 GPT-6 Astra

自 2025 年初以来，OpenAI 的 Computer Use 经历了数轮迭代，网络上许多现存资料已经过时。简而言之：早期的 Operator 以及旧版 Agent Mode 均已停用。 当前官方的主流能力依托于 GPT-6 Astra 内置的 computer_use 工具，在面向个人与办公端，通过 ChatGPT Work 与 Codex 桌面客户端提供服务；在开发者端，则通过 Responses API 开放接入。

早期技术基线（CUA / Operator，已停用）：当时采用名为 Computer-Using Agent（CUA）的模型，基于 GPT-4o 视觉能力栈结合强化学习构建。在感知层面，它仅依赖纯像素截图；OpenAI 官方评测文档明确指出，它不会解析 DOM 结构或无障碍树（Accessibility Tree）。在行动层面，它输出基于绝对坐标的点击、滚动与输入指令。

遇到登录或验证码等敏感操作时，系统会触发 Takeover Mode（接管模式） 将控制权交还人工。模型训练分为两个阶段：先通过有监督微调（SFT）建立基础的 GUI 感知与元素定位能力，再利用强化学习（RL）强化推理与自我纠错能力。发布初期，它在 OSWorld 基准上取得 38.1% 的成绩，WebArena 为 58.1%，WebVoyager 为 87%，在当时处于 SOTA 水平。

现役架构（GPT-6 Astra，自 2026 年 9 月 3 日起）：

•
computer_use 在 Responses API 中已成为一项原生内置工具，与 web_search、file_search、code_interpreter、hosted_shell 以及 mcp 并列，对应模型 ID 为 gpt-6-astra。
•
感知层面依然以屏幕截图为主，然后结合其他工具的调用结果来决定下一步动作，OpenAI 官方开发者文档也明确说明了，模型“利用截图与其他工具的结果来决定下一步操作”。没有引入 DOM 解析或无障碍树（Accessibility Tree），完全延续了 CUA“视觉优先”的技术路线。

基准测试表现（引自 OpenAI 官方对比数据）：

•
OSWorld 2.0（任务平均耗时约 40 分钟）：Astra 达到 72.6%，相比之下 GPT-5.6 Sol 为 65.7%，而早期基于旧版 OSWorld 的 CUA 仅为 38.1%。
•
ScreenSpot-Pro（无外部工具辅助的纯视觉定位）：达到 92.7%，远高于对照组的 76.9%。

安全兜底机制（依据 Astra System Card 说明）：
针对所有对外调用的工具行为，系统都会对其推理过程进行异步安全审查；一旦命中风险规则，便会立即暂停生产端正在执行的任务，或直接中断当前的 API 对话。这也是唯一一个直接嵌在执行路径中的主动防御机制。

在提示词注入（Prompt Injection）防御上，有两项独立的评测指标显示其抗性有所提升：OpenAI 内部的间接注入防御成功率从 96.23% 提升至 99.79%；在第三方 Gray Swan 的 IPI Arena 测试中，被攻击成功率从 27.0% 下降至 8.5%（注意这是两套不同口径的指标，不可互相混淆）。

在压力测试中，OpenAI 发现如果移除生产环境的安全护栏，旧版 Sol 的越权操作率会飙升至 48%；而在护栏开启的状态下，Astra 在 Computer Use 安全压力测试中出现意外非预期结果的概率仅为 2.4%，作为对比，OpenAI 测试下的 Claude Fable 5.1 为 9.5%，Opus 5 为 11.5%（OpenAI 单方给出的对比数据）。

不过这里存在一个隐患：整套安全监控高度依赖对模型思维链的读取与解析，而 Astra 的思维链（Chain-of-Thought）比上一代更难被外部有效监控；在对抗性测试压力下，模型有可能通过“伪装/隐藏真实意图（sandbagging）”绕过监控检查。对于 Computer Use 这种“每一步操作都会在现实系统产生实际副作用”的工具而言，这是一个切实存在的安全风险。

桌面端插件：完全不同维度的控制层

在面向开发者的 API 工具之外，还有一个独立面向普通消费者的产品形态：ChatGPT 桌面客户端内的 Computer Use 插件。它并非另一个 API 工具，而是专为桌面智能体设计的本地系统控制层，通过直接获取 macOS / Windows 的系统级权限，让模型能够在你的实体电脑上执行操作。正如 OpenAI 官方所言：“让 ChatGPT 在工作时代你操作各类桌面软件。”

Responses API

旧版的 computer_use_preview 模型现已正式停用。目前正式商用（GA）的接口形态为原生内置的 type: "computer" 工具，支持 gpt-5.4、gpt-5.6-sol 以及 gpt-6-astra；需要特别注意的是，Astra 的工具调用能力仅通过全新的 Responses API 提供支持，不再向后兼容旧版的 Chat Completions 接口。

按照 OpenAI 官方接入指南，目前主要有三种落地集成路径：

•
内置 Computer 运行回路：配置 tools: [{type: "computer"}]，模型会直接返回结构化的动作指令。这种方式最适合纯视觉界面的自动化交互场景。
•
自定义执行框架（Custom harness）：由开发者自行结合 Playwright、Selenium、VNC 或 MCP 进行驱动调度。适合已有既定测试与执行基建、希望沿用常规工具调用语义的工程团队。
•
代码执行路径（Code execution）：模型自行编写 PyAutoGUI 或 Playwright 脚本，并在沙箱环境中执行。这是 OpenAI 针对 Astra 官方重点推荐的方案，实现了 DOM 结构与纯视觉感知的有机结合。
