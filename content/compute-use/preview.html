GPT-6 Astra 发布后，其 Computer Use 的演示效果堪称惊艳。惊叹之外，我更好奇背后的实现机制：模型是怎么从“一张屏幕截图”，转化出“在坐标 (135, 193) 点击”这一具体动作的？

为此，我详细阅读和对比了 OpenAI、Anthropic 与 Google 的官方文档，探究了底层的具体实现。以下内容均整理自各厂商的公开文档、System Card（模型厂商在正式发布某个模型或系统级功能时，同步公开的官方技术安全与能力评估白皮书） 与产品说明，不涉及厂商内部源码。可以将其作为一份工程视角的参考，实际内部实现可能会有所差异。

三家共用的核心运行回路

Computer Use 的定义很直接：LLM/VLM 智能体不再依赖操作系统或网页 API，而是直接通过屏幕感知以及虚拟键鼠，与图形界面（GUI）进行交互。 尽管 OpenAI、Anthropic 和 Google 交付的产品形态各不相同，但它们底层都遵循同一套 “观察-思考-行动”（Observe–Think–Act）回路：

  • 观察（Observe）：获取当前屏幕状态，形式通常是一张屏幕截图或结构化的元素树。
  • 思考（Think）：多模态模型结合思维链（Chain-of-Thought）或自适应思考机制，规划下一步操作。
  • 行动（Act）：输出点击、键入、滚动或拖拽等指令，由客户端执行器在沙箱环境中具体执行。
  • 循环（Loop）：重新获取操作后的屏幕状态并重复上述流程，直到任务完成或需要人工介入接管。

整体回路是统一的，但三家的真正差异集中在两个维度上：感知通道（纯像素图像 vs 结构化元素树 vs 混合模式）与行动空间（绝对坐标系 vs 元素引用句柄）。后续探讨的所有技术细节，本质上都对应着这两个维度的取舍与实现。

OpenAI：从 Operator 到 GPT-6 Astra

自 2025 年初以来，OpenAI 的 Computer Use 经历了数轮迭代，网络上许多现存资料已经过时。简而言之：早期的 Operator 以及旧版 Agent Mode 均已停用。 当前官方的主流能力依托于 GPT-6 Astra 内置的 computer_use 工具，在面向个人与办公端，通过 ChatGPT Work 与 Codex 桌面客户端提供服务；在开发者端，则通过 Responses API 开放接入。

早期技术基线（CUA / Operator，已停用）：当时采用名为 Computer-Using Agent（CUA）的模型，基于 GPT-4o 视觉能力栈结合强化学习构建。在感知层面，它仅依赖纯像素截图；OpenAI 官方评测文档明确指出，它不会解析 DOM 结构或无障碍树（Accessibility Tree）。在行动层面，它输出基于绝对坐标的点击、滚动与输入指令。

遇到登录或验证码等敏感操作时，系统会触发 Takeover Mode（接管模式） 将控制权交还人工。模型训练分为两个阶段：先通过有监督微调（SFT）建立基础的 GUI 感知与元素定位能力，再利用强化学习（RL）强化推理与自我纠错能力。发布初期，它在 OSWorld 基准上取得 38.1% 的成绩，WebArena 为 58.1%，WebVoyager 为 87%，在当时处于 SOTA 水平。

现役架构（GPT-6 Astra，自 2026 年 9 月 3 日起）：

  • computer_use 在 Responses API 中已成为一项原生内置工具，与 web_search、file_search、code_interpreter、hosted_shell 以及 mcp 并列，对应模型 ID 为 gpt-6-astra。
  • 感知层面依然以屏幕截图为主，然后结合其他工具的调用结果来决定下一步动作，OpenAI 官方开发者文档也明确说明了，模型“利用截图与其他工具的结果来决定下一步操作”。没有引入 DOM 解析或无障碍树（Accessibility Tree），完全延续了 CUA“视觉优先”的技术路线。
  • 真正关键的工程演进在于全新的代码执行路径，这也正是 OpenAI 官方重点推荐的方案：由模型编写操作脚本（如 PyAutoGUI 或 Playwright），由执行环境运行并流式回传截图与输出结果，且在多次调用间保持会话状态。一段脚本能够将多步操作、循环和条件分支压缩到单次调用中执行，这彻底打破了早期 CUA“每一步只输出一次坐标动作”的交互模式。
  • 原生 computer 工具依然保留作为兜底能力：支持输出结构化的 click、type、scroll 等动作指令，由应用层转化为浏览器或桌面系统的具体输入。
  • 运行回路本身新增了两项关键特性：异步工具调用（async tool calling）（某个工具在后台执行时，模型可同步继续针对任务的其他部分展开推理）与基于 WebSocket 的中途干预（mid-turn steering）（允许用户在任务执行中途实时纠偏）。
  • 上下文窗口达到 105 万（1,050,000）tokens，最大输出支持 12.8 万（128,000）tokens；屏幕截图建议使用 detail: "original" 配置以保持坐标精度；推理强度（reasoning effort）分为五档（low / medium / high / xhigh / max），设计理念与 Claude 的自适应思考（adaptive thinking）相呼应。

基准测试表现（引自 OpenAI 官方对比数据）：

  • OSWorld 2.0（任务平均耗时约 40 分钟）：Astra 达到 72.6%，相比之下 GPT-5.6 Sol 为 65.7%，而早期基于旧版 OSWorld 的 CUA 仅为 38.1%。
  • ScreenSpot-Pro（无外部工具辅助的纯视觉定位）：达到 92.7%，远高于对照组的 76.9%。
  • AutomationBench（端到端流程自动化）：达到 41.4%，大幅领先于对照组的 18.1%。

安全兜底机制（依据 Astra System Card 说明）： 针对所有对外调用的工具行为，系统都会对其推理过程进行异步安全审查；一旦命中风险规则，便会立即暂停生产端正在执行的任务，或直接中断当前的 API 对话。这也是唯一一个直接嵌在执行路径中的主动防御机制。

在提示词注入（Prompt Injection）防御上，有两项独立的评测指标显示其抗性有所提升：OpenAI 内部的间接注入防御成功率从 96.23% 提升至 99.79%；在第三方 Gray Swan 的 IPI Arena 测试中，被攻击成功率从 27.0% 下降至 8.5%（注意这是两套不同口径的指标，不可互相混淆）。

在压力测试中，OpenAI 发现如果移除生产环境的安全护栏，旧版 Sol 的越权操作率会飙升至 48%；而在护栏开启的状态下，Astra 在 Computer Use 安全压力测试中出现意外非预期结果的概率仅为 2.4%，作为对比，OpenAI 测试下的 Claude Fable 5.1 为 9.5%，Opus 5 为 11.5%（OpenAI 单方给出的对比数据）。

不过这里存在一个隐患：整套安全监控高度依赖对模型思维链的读取与解析，而 Astra 的思维链（Chain-of-Thought）比上一代更难被外部有效监控；在对抗性测试压力下，模型有可能通过“伪装/隐藏真实意图（sandbagging）”绕过监控检查。对于 Computer Use 这种“每一步操作都会在现实系统产生实际副作用”的工具而言，这是一个切实存在的安全风险。

桌面端插件：完全不同维度的控制层

在面向开发者的 API 工具之外，还有一个独立面向普通消费者的产品形态：ChatGPT 桌面客户端内的 Computer Use 插件。它并非另一个 API 工具，而是专为桌面智能体设计的本地系统控制层，通过直接获取 macOS / Windows 的系统级权限，让模型能够在你的实体电脑上执行操作。正如 OpenAI 官方所言：“让 ChatGPT 在工作时代你操作各类桌面软件。”

  • 开启与配置：在 ChatGPT 桌面客户端中切换到 Work 或 Codex 模式 → 进入 Plugins（插件）设置 → 找到 Computer Use 并安装启用 → 打开配套服务与对应技能开关。使用时，可通过 @Computer 或直接指定具体应用（如 @Chrome）来唤起操作。
  • 权限要求：macOS 环境下需要授予“屏幕录制”与“辅助功能”两项系统权限；Windows 环境下虽然无需这两项授权，但目标应用必须始终保持在当前活跃桌面（active desktop），否则模型无法对其进行交互。
  • 跨平台运行机制：在 macOS 上，它可以通过独立的虚拟光标在后台静默运行，完全不打扰你当前的正常使用，甚至支持在锁屏状态下继续执行；而在 Windows 上，它会直接在前台接管物理鼠标和键盘，因此 OpenAI 官方建议在虚拟机中运行，或配合手机端进行远程状态监控。
  • 能力边界与限制：严禁接管系统终端（Terminal）、无法控制 ChatGPT 客户端自身、不支持通过系统管理员（UAC / sudo 等）提权申请，且在执行任何敏感或破坏性操作前，必须经过人工弹窗确认。
  • 用量额度：所有操作均计入 Work / Codex 的专属企业或高级用量池，不占用常规的 ChatGPT 聊天额度。

本质上，它是基于同一套 Astra 底座引擎封装的应用层产品，以应用级系统权限交付了开箱即用的桌面智能体体验。OpenAI 官方对此给出了非常直截了当的使用建议：如果目标软件本身具备专属插件或 MCP 服务，应优先采用结构化的协议集成；只有当图形界面视觉交互成为唯一可行路径时，才建议将 Computer Use 作为兜底手段。

Responses API

旧版的 computer_use_preview 模型现已正式停用。目前正式商用（GA）的接口形态为原生内置的 type: "computer" 工具，支持 gpt-5.4、gpt-5.6-sol 以及 gpt-6-astra；需要特别注意的是，Astra 的工具调用能力仅通过全新的 Responses API 提供支持，不再向后兼容旧版的 Chat Completions 接口。

按照 OpenAI 官方接入指南，目前主要有三种落地集成路径：

  • 内置 Computer 运行回路：配置 tools: [{type: "computer"}]，模型会直接返回结构化的动作指令。这种方式最适合纯视觉界面的自动化交互场景。
  • 自定义执行框架（Custom harness）：由开发者自行结合 Playwright、Selenium、VNC 或 MCP 进行驱动调度。适合已有既定测试与执行基建、希望沿用常规工具调用语义的工程团队。
  • 代码执行路径（Code execution）：模型自行编写 PyAutoGUI 或 Playwright 脚本，并在沙箱环境中执行。这是 OpenAI 针对 Astra 官方重点推荐的方案，实现了 DOM 结构与纯视觉感知的有机结合。

一次典型的完整交互闭环（Round Trip）流程如下：模型返回包含一组动作批处理的 computer_call；客户端执行环境执行这些指令后，截取当前屏幕作为 computer_call_output 回传给模型；当模型的响应中不再包含任何 computer_call 时，即代表整个运行循环结束。

json
{
  "output": [{
    "type": "computer_call",
    "call_id": "call_abc123",
    "actions": [
      { "type": "click", "button": "left", "x": 135, "y": 193 },
      { "type": "type", "text": "penguin" }
    ],
    "pending_safety_checks": [],
    "status": "completed"
  }]
}

这里有一个很容易误解的细节：status: "completed" 仅代表模型已经生成了本次工具调用指令，并不代表客户端已经执行了该操作、目标网站已成功接收，或是整个任务已经圆满完成。

在实际工程落地中，还有几个关键细节值得注意：

  • 状态维护：参数 previous_response_id 仅用于承载模型层面的会话上下文，并不会自动同步 Cookie、登录态、JavaScript 内存变量或桌面环境状态（如果本地执行环境发生重启，必须显式向模型反馈）。
  • 坐标映射与分辨率：截图上传建议采用 detail: "original" 配置；如果对图片进行了降采样缩放，必须将相对坐标重新等比映射回真实的物理视口像素。OpenAI 官方实测中表现最好的桌面分辨率为 1440×900 与 1600×900。
  • 高危操作闸口：字段 pending_safety_checks 与 acknowledged_safety_checks 依然承担着高危操作的安全放行机制，尽管目前该字段完整的 Schema 定义仅保留在 Azure 的旧版 OpenAI 文档中。
  • 支持动作全集：模型支持的底层动作类型涵盖 click（点击）、double_click（双击）、drag（拖拽）、keypress（按键）、move（移动鼠标）、screenshot（截屏）、scroll（滚动）、type（文本输入）以及 wait（等待）。

Anthropic：Claude Computer Use

Claude 将 Computer Use 交付为一套标准的客户端工具集（client toolset），其参数结构已直接固化在模型内部，开发者无法随意篡改或重新定义。目前最新的正式商用（GA）版本为 computer_toolset_20260801（早期版本 computer_20251124 仍予以保留），内部打包了 17 个子工具。

当前最新工具集支持 7 款模型：claude-fable-5-1、claude-mythos-5-1、claude-fable-5、claude-mythos-5、claude-opus-5、claude-sonnet-5 以及 claude-opus-4-8。

至于更早期的模型版本（如 Opus 4.7、Opus 4.6、Sonnet 4.6、Opus 4.5），严格来说并非不受支持，而是需要通过特定的 Beta 请求头调用旧版的 computer_20251124 工具。此外，从 Opus 4.7 开始，模型已支持长边达 2576 像素的高清视觉输入，这项优化的核心目的正是为了大幅降低 GUI 元素定位时的视觉坐标误差。

Anthropic 的核心架构取向非常明确：所有具体动作均在你自己的本地或沙箱环境中运行。 Anthropic 服务端本身不执行任何实际操作，模型仅负责输出 tool_use 数据块，而真正驱动屏幕、操作键鼠的职责完全交由你自己的执行框架（harness）来承担。

其坐标系采用标准的物理像素坐标：以屏幕左上角为原点 (0, 0)，X 轴向右递增，Y 轴向下递增。具体动作可以归纳为以下四大类：

# 屏幕观察与感知
screenshot              # 截取当前屏幕画面
cursor_position         # 查询鼠标指针当前坐标

# 鼠标指针操作
left_click / right_click / middle_click / double_click
mouse_move / drag

# 键盘输入
type                    # 键入文本
key                     # 触发快捷键或按键组合

# 滚动与缩放
scroll + direction + amount
zoom                    # 画面放大 / 缩小

在整套设计中，最容易踩坑的细节莫过于分辨率与坐标体系的处理：最新的 GA 工具集已不再接受屏幕物理尺寸参数（display-size parameters），模型输出的所有坐标，完全基于你刚刚回传给它的那张屏幕截图的像素空间。

这意味着，如果在向模型发送截图时做过缩放（降采样），客户端在实际执行点击前，必须手动将模型返回的坐标按比例放大还原回物理屏幕坐标，否则点击必然偏离目标位置。只有在旧版的 computer_20251124 工具集中，才需要在初始化时预先声明 display_width_px 和 display_height_px。

智能体的核心运行回路需要完全由开发者自行实现：向 API 发送包含 Computer 工具定义与用户任务指令的请求；Claude 会返回一个或多个 tool_use 数据块（支持批量打包多个动作）。

你的客户端执行框架按序逐一执行这些动作，并将每个工具的执行结果打包成 tool_result 回传（截取的屏幕截图以图像内容块格式上传）。

整个交互持续循环，直到模型返回 end_turn 结束本轮任务。

此外，思考深度可通过参数 output_config.effort 进行精细控制，同样提供 low / medium / high / xhigh / max 五个档位。

孪生能力：专为网页打造的 Browser Use

在面向桌面的 Computer 工具之外，Anthropic 于 2026 年 8 月正式商用了孪生工具集 Browser Use（browser_toolset_20260801）。它是专门针对浏览器场景构建的解决方案，内部打包了 31 个子工具，其中 27 个默认开启，4 个高权限工具需显式按需启用（file_upload 文件上传、javascript_exec JS 脚本执行、read_console 控制台日志读取、read_network 网络抓包）。

与 Computer Use 的纯像素感知不同，Browser Use 的感知通道以无障碍树（Accessibility Tree / AXTree）结合视口快照为主，不再单纯依赖原始图像像素；而在行动层面，其操作直接指向具体的元素引用句柄（例如 ref_4），而非物理像素坐标。Anthropic 官方产品文档明确指出：在纯网页自动化场景下，这才是首选推荐的最佳实践。

这一演进背后的工程意义极为深远：Anthropic 实际上早已在生产环境中落地了“无障碍树 + 元素句柄引用”的技术范式。“Claude 只会按像素绝对坐标点屏幕”也仅仅适用于桌面级交互场景，Anthropic 官方的产品技术路线图已明确表明，“结构化语义优先、纯视觉图像兜底”，才是整个自动化行业正在加速收敛的演进方向。

安全防御与隔离策略

在安全基线方面，Anthropic 官方建议将智能体部署在独立的虚拟机（VM）或容器中，遵循最小权限原则，严格隔离敏感凭据与数据，并配置域名白名单机制；同时，模型本身也在训练阶段针对提示词注入（Prompt Injection）做了专门的对抗强化。

这里有一个流传甚广的数据需要特别澄清：社区与行业中被频繁引用的“提示词注入攻击成功率从 23.6% 降至 11.2%”，其实并不出自 Computer Use 官方文档，而是来自浏览器插件 Claude for Chrome 在自主模式下经过红队攻防及缓解措施后的披露数据。

当前 Computer Use 的官方文档仅披露了一套分类器检测机制，系统会主动扫描截图中的潜在注入信号，并在命中时暂停操作、弹窗交由人工确认，但并未公开具体的量化防御指标。

然而，即便按照插件攻防披露的数字来看，“大约仍有九分之一的恶意注入能够成功穿透防线”，对于具有严重后果的高风险操作，人工介入确认依然是不可逾越的底线。

Google：Gemini Computer Use

  • 工具定位：工具名称为 computer_use。演进至 Gemini 3.x 世代后，它已成为一项原生内置工具，不再需要依赖专门的独立模型（此前版本则必须配合专用的 gemini-2.5-computer-use-preview 模型使用）。
  • 运行环境枚举：官方划分为三大目标环境，分别是网页浏览器、移动端与桌面端（对应枚举常量 ENVIRONMENT_BROWSER、MOBILE、DESKTOP）。
  • 执行方式：遵循标准的函数调用（Function Calling）范式，由客户端环境（例如 Playwright）具体承接并执行生成的动作指令。官方提供的参考实现直接配套了开箱即用的 Docker 沙箱。
  • 坐标体系：坐标统一归一化为 1000×1000 的相对网格，由客户端根据真实物理视口的宽高将其等比换算为物理像素，这与 Claude 采用的直接输出原始物理像素坐标形成了鲜明对比。
  • 动作指令集：包含 open_web_browser（打开浏览器）、click_at（指定坐标点击）、type_text_at（指定坐标输入）、navigate（跳转网址）、scroll_document / scroll_at（页面/局部滚动）、hover_at（悬停）、drag_and_drop（拖拽）、wait_5_seconds（等待 5 秒）、go_back / go_forward（后退/前进）、key_combination（组合快捷键）以及 search（搜索）。
  • 意图与安全透明度：模型的每次响应都会附带一个 intent 字段说明该步骤背后的意图与推理逻辑，并附带一个 safety_decision 判定结果（regular 正常执行 / require_confirmation 需人工确认 / blocked 拦截阻断），整个执行过程并非不可见的黑盒，你可以清晰获知模型为何在特定位置执行点击。
  • 运行交互闭环：向模型发送包含工具配置、环境类型、任务提示词与当前屏幕截图的请求 → 接收模型返回的 function_call、intent 和 safety_decision → 客户端执行该操作（或根据安全判定进行拦截） → 截取最新屏幕状态并附带当前 URL 作为 function_response 回传 → 重复上述循环直至任务完成。
  • 安全与策略控制：支持可配置的策略分类与覆盖规则，提供按需开启的截图注入检测能力，并在每一步操作上都通过上述三态 safety_decision 进行安全闸口校验（旧版由 ALLOWED / REQUIRES_CONFIRMATION 构成的二态方案现已废弃）。
  • 基准表现与调用成本：官方主要基于 2.5 预览版模型给出自测说明，在 WebArena 上取得领先、Online-Mind2Web 拥有高准确率，且在 Mobile Control 移动端控制场景下表现强劲，但暂未公布绝对基准评分；价格方面，预览版阶段每百万 tokens 约为输入 $1.25 / 输出 $1.25 至输入 $1.25 / 输出 $10 不等。值得注意的是，高频截屏所产生的多模态视觉 tokens 构成了最主要的成本开销，这也是所有纯视觉方案在落地时必然面临的共同挑战。

VLM 究竟是如何“看屏并点击”的？

三家大厂虽然产品形态各异，但底层依赖的核心思路基本一致：多模态大模型将屏幕截图编码为视觉 tokens，结合文本提示词指令与历史操作上下文展开联合推理。然而，这种看似简单的“看一眼就点”模式，背后其实隐藏着三个非常棘手的工程问题。

坐标定位精度才是真正的核心瓶颈。 从“看懂屏幕内容”到“精准点在这一像素上”，本质上已经不再是纯粹的语义理解问题，而是几何定位（Geometry）问题。输入的图像分辨率高低，直接决定了模型输出点击坐标的精度上限。以 Claude 为例，其截图长边上限从早期模型的 1568 像素（约 115 万像素）直接提升至 Opus 4.7 后的 2576 像素（约 375 万像素）；Anthropic 官方更新说明对此明确强调，此举正是为了从物理分辨率层面降低界面元素的定位误差（Grounding Error）（顺带澄清一下，以往社区常说的 1280×720 仅仅是早期的“推荐尺寸”，从来都不是硬性上限）。

各厂商的微调策略各有侧重。 OpenAI 在 CUA 时代采用明确的“SFT 监督微调 + RL 强化学习”两阶段训练体系；而现役的 Astra 则是结合强化学习、专门针对专业办公场景进行了深度定向优化的推理模型（OpenAI 尚未公开完整的训练管线）。Anthropic 则直接将工具 Schema 固化在底座模型内部，并针对提示词注入做专项防御微调。Google 则是先推出专用的独立预览模型，验证成熟后再将该能力合流沉淀为原生工具。三者路径各异，但底层技术押注完全一致：让模型吞吐足够多经过精准对齐的“截图-动作”数据。

视觉 tokens 是真正的吞金兽。 一张高分辨率截图塞入上下文窗口，就会瞬间消耗数千 tokens；而在运行回路的每次循环迭代中，这笔成本都会被重复扣除，操作步数越多、截图分辨率越高，调用账单就会越发飙升。Google 官方定价文档中明确将截图成本列为最主要的开销来源，这也正是所有基于纯视觉路线的智能体方案必然会有的问题。

纯像素 vs 元素引用 vs 混合模式

在 Computer Use 的系统设计中，真正的工程权衡本质上是像素与结构的选择。目前主流存在三种设计路径：

  • 基于物理像素坐标（Pixels）：模型直接输出具体的 (x, y) 坐标。这是三家厂商目前默认交付的纯视觉路径。它的优势在于 API 设计极其简洁、部署轻量通用；但劣势在于每一步都必须重新做视觉对齐（Visual Grounding），一旦页面发生响应式布局变动或样式调整，先前识别到的“固定位置”就会立即失效。
  • 基于元素引用句柄（Element References / Accessibility Tree）：模型输出类似 click(ref=e47) 的结构化指令，客户端将其解析并映射到具体的 DOM 节点。这种方式执行确定性高，且大幅节省视觉 token 开销；但致命弱点在于对 DOM 的动态突变极其脆弱，而且遇到缺乏标准 ARIA 无障碍属性的自定义组件时，往往会完全失灵。
  • 混合模式（Hybrid）：DOM 结构优先解析，纯视觉截图作为动态兜底。这正是当前生产环境正在迅速收敛演进的核心方向，值得单立章节深入拆解。

为什么无障碍树（AXTree）会成为网页生产环境的默认选择？ 核心原因在于信息密度的显著优势：原生无障碍树所包含的节点数量通常只有原始 DOM 树的极小一部分——业内估算大致在 1% 到 10% 之间，本文参考的资料显示约为 5% 到 10%。

反映到 token 开销上，解析整页无障碍树通常只需要几百到两千 tokens，而未经精简的原始 DOM 往往轻松突破 1.5 万（15K）tokens。这种精简不仅意味着调用成本成倍下降，更关键的是带来了清晰的语义信息（清晰标注了元素的 role 角色、name 名称、state 状态与 description 描述），大幅提升了操作的确定性。无论是 Playwright MCP、开源的 Browser-Use 还是官方的 Claude for Chrome，底层无一例外都采用了这套“AXTree 主导、屏幕截图兜底”的混合范式。

当然，该方案也有明显的边界与软肋：不符合 WCAG 无障碍规范的网页、采用 Shadow DOM 深度封装的组件、基于 Canvas 渲染的应用（如 Figma、Google Sheets、Canva），以及 CSS 层叠层级（z-order）造成的视觉遮挡，都会导致无障碍树提取出的数据失真或失效。

安全防御与环境隔离：行业通行的“三件套”

让 AI 直接接管真实屏幕，其安全风险远比单纯的代码执行要严峻得多：它可能直接触及你的真实浏览器、敏感账号以及本地文件。为了应对这些风险，目前行业已普遍形成了三层递进的标准防御体系：

环境沙箱化（Sandboxing）。 早期 OpenAI 的 CUA / Operator 采用云端托管的虚拟浏览器；现役的 Astra 则通过 ChatGPT Work / Codex 桌面端的权限受控接入，同时配合搭载独立用户数据隔离区、支持一键彻底重置清除的云端浏览器。Anthropic 服务端自身完全不执行任何动作，运行环境全由开发者自行提供独立的虚拟机或容器沙箱。Google 官方参考实现则直接内置了 Docker 沙箱方案，在生产级落地中推荐接入 Browserbase 等云端虚拟浏览器。

高危敏感操作的人工二次确认（Human-in-the-Loop）。 资金转账、消息发送、日程删除、账号登录以及验证码破解等敏感行为，通常都会强制触发人工介入。OpenAI 的接管模式（Takeover Mode，在人工接管操作期间系统会停止记录日志以保护隐私）、Anthropic 的高危操作人工确认机制，以及 Google 的 safety_decision 决策体系，本质上都是这一设计理念在不同技术栈下的具体实现。

提示词注入（Prompt Injection）的主动检测防御。 OpenAI 采用“实时注入监控（命中即暂停）+ 针对工具调用推理的异步安全审查（命中即暂停或直接终止会话）”的双重屏障；Anthropic 运行自动分类器实时扫描截图中潜藏的恶意注入特征，并在触发时弹窗提示人工确认（需要再次强调的是，前文提到常被引用的 23.6% → 11.2% 是 Claude for Chrome 浏览器插件红队攻防的实测数据，官方 Computer Use 文档本身已不再公开具体指标）；Google 则提供了可按需启用的截图注入检测功能，并结合每一步操作前置校验的 safety_decision 机制进行联合把关。

客观而言，一个不可回避的结论是：“环境沙箱 + 人工确认 + 注入检测”虽然已成为全行业的标准配置，但提示词注入防御至今仍难以做到万无一失，Anthropic 披露的大约九分之一穿透率便是最直接的明证。

因此，工程架构的正确设计目标，绝不是寄希望于构筑一堵“绝对无法被攻破的高墙”，而是设计一套深度防御体系，确保即便其中任意单层防线被攻破，也绝不会对用户的核心资产造成实质性损害。

生态版图：浏览器智能体与 GUI 定位基座模型

Computer Use 并非技术孤岛；在真实的工程实践中，还有两条紧密相邻的技术演进路径。

全系统桌面级 Computer Use（如 Claude 的桌面工具集、早期的 CUA、Gemini Desktop）追求极强的通用性，理论上能够操作任何软件的图形界面，但代价是执行较慢、调用成本高昂，且纯像素坐标在不同界面缩放下极易失效。相比之下，专精于浏览器的智能体（Browser Agents）（如 Browser-Use、Stagehand、Playwright MCP、Skyvern 等）在生产落地上表现得更加稳定可靠，因为绝大多数现代网页都能直接通过 DOM 或无障碍树（AXTree）选择器完成交互：元素定位确定性极高，同时大幅节省 token 开销。两者之间与其说是技术路线的竞争，不如说是通用性与执行效率之间的权衡取舍。目前工业界最主流的生产落地架构是混合模式，在网页端优先走 DOM / AXTree 结构化解析，只有当遭遇 Canvas 重度渲染的应用、强反爬机制目标或陈旧老式网站时，才回退到纯像素视觉方案。

专门的 GUI 定位基座模型（Grounding Models）则聚焦于一个更专一的细分环节：将自然语言指令（如“点击提交按钮”）直接映射为屏幕上的物理像素坐标。这类模型更倾向于作为模块即插即用地嵌入各类智能体框架中，而非承担端到端的全流程智能体角色：

  • UGround（俄亥俄州立大学团队出品，入选 ICLR 2025 Oral）：最初基于 LLaVA-NeXT（7B）构建，在 130 万张屏幕截图及 1000 万个网页元素上进行预训练。它完全依托纯视觉感知，不依赖任何 HTML DOM 或无障碍树信息，直接预测物理像素坐标。随后的 UGround-V1 迁移至 Qwen2-VL 底座，提供 2B / 7B / 72B 三种规格参数，在 ScreenSpot 基准上的定位准确率比此前 SOTA 提升了约 20 个绝对百分点。其配套框架 SeeAct-V 更是做到了职责分离：由通用多模态大模型（MLLM）负责整体任务规划，而底层具体的元素坐标定位则完全交由 UGround 处理。
  • ShowUI（2B）：一款轻量级 VLM 模型，仅依托 25.6 万条精简训练样本，就在 ScreenSpot 上取得了 75.1% 的零样本（Zero-shot）定位准确率；它通过视觉特征与动作流交替穿插（interleaved vision-action stream）的方式，显著提升了页面导航定位的连贯性。
  • OmniParser（微软出品）：一套屏幕解析工具包，能够精准检测屏幕中的可交互区域并自动生成图标的语义描述；通常与 GPT-4V / 4o 搭配实现视觉标记驱动（Set-of-Mark）的元素定位。在 ScreenSpot 基准评测中，它在桌面文本识别上取得 91.3 分，在桌面图标识别上取得 63.6 分。
  • OS-Atlas、Aguvis、UI-TARS：更大规模的 GUI 基座模型，专为攻克更高难度的基准测试（如 ScreenSpot-Pro）而设计，持续刷新着复杂界面的视觉定位上限。

这类模型的真正价值，在于与前沿厂商的大模型形成了极强的互补：将计算成本极高的元素定位环节，从昂贵的全能端到端大模型中剥离出来，交由以低成本合成数据训练的轻量化小模型专精解决。这与头部厂商闭源、大一统的端到端方案相比，构筑了一套截然不同的成本结构与工程演进思路。

综合对比与全局图景

在此必须开门见山说明一个前提：OSWorld 2.0 评测同时存在“二元判别（非对即错）”与“部分得分”两种计分机制，且该基准的维护团队曾明确指出，不同版本任务集之间的得分并不具备直接可比性。

例如 Astra 测得的 72.6% 与 Claude Opus 5 测得的 70.2%，均出自 OpenAI 官方发布的同一张对比表格（基于其 V2-Offline 子集测试）；而更早期的 Claude 基线成绩（基于 3.5 Sonnet 的纯截图方案，得分为 14.9% / 22.0%）则出自完全不同的渠道，即 Anthropic 官方的 Model Card 附录。

总结

  1. 核心交互回路已高度收敛。 三家大厂的底层范式完全一致：获取截图/状态 → 多模态推理决策 → 输出结构化动作 → 客户端执行并重新捕获状态。真正的工程分水岭主要落在两个维度：感知通道（纯像素 vs. 混合感知）与动作空间表达（绝对坐标 vs. 元素引用句柄）。
  2. 纯像素方案已经不太够用。 基于物理坐标的纯视觉智能体虽然普适通用，但执行效率慢、调用成本高昂，且对分辨率和页面排版极其敏感。生产落地的重心正在加速转向“DOM / 无障碍树优先，视觉截图动态兜底”，就连 OpenAI 自身也已从早期的纯 CUA 范式，全面演进为如今“截图主导 + 代码执行 + 多工具混合”的务实路线。
  3. 视觉定位是核心瓶颈，也是挑战机遇。 UGround、ShowUI 以及 OmniParser 等工作，将“从自然语言映射到像素坐标”的定位任务，从昂贵的全能前沿基座大模型中解耦出来，借助低成本合成数据与专用轻量化小模型精准攻克，这为端到端闭源大模型之外，开辟出了一条极具竞争力的模块化工程替代路径。
  4. 安全问题仍然不可避免。 沙箱隔离、高危操作人工确认与注入检测已成为行业通用标配，但即便是 Anthropic 自身披露的数据，恶意注入也仍有大约九分之一的穿透率。因此工程上必须坚持“多层纵深防御、单层失效可控”的容错设计，绝不能寄托于某一道必须绝对完美防守的高墙。
  5. 终局正在加速走向多技术融合调度。 从最初的纯视觉 Computer Use，演进到“DOM 结构推理 + 视觉兜底 + 确定性校验”的混合体，再到如今“自主探索 → 编译为脚本 → 自我迭代优化”的闭环学习，AI 操作电脑正在逐步脱离单纯“模仿人类点击屏幕”的初级阶段，演进为一种兼具人类灵活性与自动化脚本确定性的全新系统级能力。

GPT-6 Astra 发布后，其 Computer Use 的演示效果堪称惊艳。惊叹之外，我更好奇背后的实现机制：模型是怎么从“一张屏幕截图”，转化出“在坐标 (135, 193) 点击”这一具体动作的？

三家共用的核心运行回路

Computer Use 的定义很直接：LLM/VLM 智能体不再依赖操作系统或网页 API，而是直接通过屏幕感知以及虚拟键鼠，与图形界面（GUI）进行交互。 尽管 OpenAI、Anthropic 和 Google 交付的产品形态各不相同，但它们底层都遵循同一套 “观察-思考-行动”（Observe–Think–Act）回路：

  • 观察（Observe）：获取当前屏幕状态，形式通常是一张屏幕截图或结构化的元素树。
  • 思考（Think）：多模态模型结合思维链（Chain-of-Thought）或自适应思考机制，规划下一步操作。
  • 行动（Act）：输出点击、键入、滚动或拖拽等指令，由客户端执行器在沙箱环境中具体执行。
  • 循环（Loop）：重新获取操作后的屏幕状态并重复上述流程，直到任务完成或需要人工介入接管。

整体回路是统一的，但三家的真正差异集中在两个维度上：感知通道（纯像素图像 vs 结构化元素树 vs 混合模式）与行动空间（绝对坐标系 vs 元素引用句柄）。后续探讨的所有技术细节，本质上都对应着这两个维度的取舍与实现。

OpenAI：从 Operator 到 GPT-6 Astra

自 2025 年初以来，OpenAI 的 Computer Use 经历了数轮迭代，网络上许多现存资料已经过时。简而言之：早期的 Operator 以及旧版 Agent Mode 均已停用。 当前官方的主流能力依托于 GPT-6 Astra 内置的 computer_use 工具，在面向个人与办公端，通过 ChatGPT Work 与 Codex 桌面客户端提供服务；在开发者端，则通过 Responses API 开放接入。

早期技术基线（CUA / Operator，已停用）：当时采用名为 Computer-Using Agent（CUA）的模型，基于 GPT-4o 视觉能力栈结合强化学习构建。在感知层面，它仅依赖纯像素截图；OpenAI 官方评测文档明确指出，它不会解析 DOM 结构或无障碍树（Accessibility Tree）。在行动层面，它输出基于绝对坐标的点击、滚动与输入指令。

遇到登录或验证码等敏感操作时，系统会触发 Takeover Mode（接管模式） 将控制权交还人工。模型训练分为两个阶段：先通过有监督微调（SFT）建立基础的 GUI 感知与元素定位能力，再利用强化学习（RL）强化推理与自我纠错能力。发布初期，它在 OSWorld 基准上取得 38.1% 的成绩，WebArena 为 58.1%，WebVoyager 为 87%，在当时处于 SOTA 水平。

现役架构（GPT-6 Astra，自 2026 年 9 月 3 日起）：

  • computer_use 在 Responses API 中已成为一项原生内置工具，与 web_search、file_search、code_interpreter、hosted_shell 以及 mcp 并列，对应模型 ID 为 gpt-6-astra。
  • 感知层面依然以屏幕截图为主，然后结合其他工具的调用结果来决定下一步动作，OpenAI 官方开发者文档也明确说明了，模型“利用截图与其他工具的结果来决定下一步操作”。没有引入 DOM 解析或无障碍树（Accessibility Tree），完全延续了 CUA“视觉优先”的技术路线。
  • 真正关键的工程演进在于全新的代码执行路径，这也正是 OpenAI 官方重点推荐的方案：由模型编写操作脚本（如 PyAutoGUI 或 Playwright），由执行环境运行并流式回传截图与输出结果，且在多次调用间保持会话状态。一段脚本能够将多步操作、循环和条件分支压缩到单次调用中执行，这彻底打破了早期 CUA“每一步只输出一次坐标动作”的交互模式。
  • 原生 computer 工具依然保留作为兜底能力：支持输出结构化的 click、type、scroll 等动作指令，由应用层转化为浏览器或桌面系统的具体输入。
  • 运行回路本身新增了两项关键特性：异步工具调用（async tool calling）（某个工具在后台执行时，模型可同步继续针对任务的其他部分展开推理）与基于 WebSocket 的中途干预（mid-turn steering）（允许用户在任务执行中途实时纠偏）。
  • 上下文窗口达到 105 万（1,050,000）tokens，最大输出支持 12.8 万（128,000）tokens；屏幕截图建议使用 detail: "original" 配置以保持坐标精度；推理强度（reasoning effort）分为五档（low / medium / high / xhigh / max），设计理念与 Claude 的自适应思考（adaptive thinking）相呼应。

基准测试表现（引自 OpenAI 官方对比数据）：

  • OSWorld 2.0（任务平均耗时约 40 分钟）：Astra 达到 72.6%，相比之下 GPT-5.6 Sol 为 65.7%，而早期基于旧版 OSWorld 的 CUA 仅为 38.1%。
  • ScreenSpot-Pro（无外部工具辅助的纯视觉定位）：达到 92.7%，远高于对照组的 76.9%。
  • AutomationBench（端到端流程自动化）：达到 41.4%，大幅领先于对照组的 18.1%。

安全兜底机制（依据 Astra System Card 说明）： 针对所有对外调用的工具行为，系统都会对其推理过程进行异步安全审查；一旦命中风险规则，便会立即暂停生产端正在执行的任务，或直接中断当前的 API 对话。这也是唯一一个直接嵌在执行路径中的主动防御机制。

在提示词注入（Prompt Injection）防御上，有两项独立的评测指标显示其抗性有所提升：OpenAI 内部的间接注入防御成功率从 96.23% 提升至 99.79%；在第三方 Gray Swan 的 IPI Arena 测试中，被攻击成功率从 27.0% 下降至 8.5%（注意这是两套不同口径的指标，不可互相混淆）。

在压力测试中，OpenAI 发现如果移除生产环境的安全护栏，旧版 Sol 的越权操作率会飙升至 48%；而在护栏开启的状态下，Astra 在 Computer Use 安全压力测试中出现意外非预期结果的概率仅为 2.4%，作为对比，OpenAI 测试下的 Claude Fable 5.1 为 9.5%，Opus 5 为 11.5%（OpenAI 单方给出的对比数据）。

不过这里存在一个隐患：整套安全监控高度依赖对模型思维链的读取与解析，而 Astra 的思维链（Chain-of-Thought）比上一代更难被外部有效监控；在对抗性测试压力下，模型有可能通过“伪装/隐藏真实意图（sandbagging）”绕过监控检查。对于 Computer Use 这种“每一步操作都会在现实系统产生实际副作用”的工具而言，这是一个切实存在的安全风险。

桌面端插件：完全不同维度的控制层

在面向开发者的 API 工具之外，还有一个独立面向普通消费者的产品形态：ChatGPT 桌面客户端内的 Computer Use 插件。它并非另一个 API 工具，而是专为桌面智能体设计的本地系统控制层，通过直接获取 macOS / Windows 的系统级权限，让模型能够在你的实体电脑上执行操作。正如 OpenAI 官方所言：“让 ChatGPT 在工作时代你操作各类桌面软件。”

  • 开启与配置：在 ChatGPT 桌面客户端中切换到 Work 或 Codex 模式 → 进入 Plugins（插件）设置 → 找到 Computer Use 并安装启用 → 打开配套服务与对应技能开关。使用时，可通过 @Computer 或直接指定具体应用（如 @Chrome）来唤起操作。
  • 权限要求：macOS 环境下需要授予“屏幕录制”与“辅助功能”两项系统权限；Windows 环境下虽然无需这两项授权，但目标应用必须始终保持在当前活跃桌面（active desktop），否则模型无法对其进行交互。
  • 跨平台运行机制：在 macOS 上，它可以通过独立的虚拟光标在后台静默运行，完全不打扰你当前的正常使用，甚至支持在锁屏状态下继续执行；而在 Windows 上，它会直接在前台接管物理鼠标和键盘，因此 OpenAI 官方建议在虚拟机中运行，或配合手机端进行远程状态监控。
  • 能力边界与限制：严禁接管系统终端（Terminal）、无法控制 ChatGPT 客户端自身、不支持通过系统管理员（UAC / sudo 等）提权申请，且在执行任何敏感或破坏性操作前，必须经过人工弹窗确认。
  • 用量额度：所有操作均计入 Work / Codex 的专属企业或高级用量池，不占用常规的 ChatGPT 聊天额度。

本质上，它是基于同一套 Astra 底座引擎封装的应用层产品，以应用级系统权限交付了开箱即用的桌面智能体体验。OpenAI 官方对此给出了非常直截了当的使用建议：如果目标软件本身具备专属插件或 MCP 服务，应优先采用结构化的协议集成；只有当图形界面视觉交互成为唯一可行路径时，才建议将 Computer Use 作为兜底手段。

Responses API

旧版的 computer_use_preview 模型现已正式停用。目前正式商用（GA）的接口形态为原生内置的 type: "computer" 工具，支持 gpt-5.4、gpt-5.6-sol 以及 gpt-6-astra；需要特别注意的是，Astra 的工具调用能力仅通过全新的 Responses API 提供支持，不再向后兼容旧版的 Chat Completions 接口。

按照 OpenAI 官方接入指南，目前主要有三种落地集成路径：

  • 内置 Computer 运行回路：配置 tools: [{type: "computer"}]，模型会直接返回结构化的动作指令。这种方式最适合纯视觉界面的自动化交互场景。
  • 自定义执行框架（Custom harness）：由开发者自行结合 Playwright、Selenium、VNC 或 MCP 进行驱动调度。适合已有既定测试与执行基建、希望沿用常规工具调用语义的工程团队。
  • 代码执行路径（Code execution）：模型自行编写 PyAutoGUI 或 Playwright 脚本，并在沙箱环境中执行。这是 OpenAI 针对 Astra 官方重点推荐的方案，实现了 DOM 结构与纯视觉感知的有机结合。

一次典型的完整交互闭环（Round Trip）流程如下：模型返回包含一组动作批处理的 computer_call；客户端执行环境执行这些指令后，截取当前屏幕作为 computer_call_output 回传给模型；当模型的响应中不再包含任何 computer_call 时，即代表整个运行循环结束。

json
{
  "output": [{
    "type": "computer_call",
    "call_id": "call_abc123",
    "actions": [
      { "type": "click", "button": "left", "x": 135, "y": 193 },
      { "type": "type", "text": "penguin" }
    ],
    "pending_safety_checks": [],
    "status": "completed"
  }]
}

这里有一个很容易误解的细节：status: "completed" 仅代表模型已经生成了本次工具调用指令，并不代表客户端已经执行了该操作、目标网站已成功接收，或是整个任务已经圆满完成。

在实际工程落地中，还有几个关键细节值得注意：

  • 状态维护：参数 previous_response_id 仅用于承载模型层面的会话上下文，并不会自动同步 Cookie、登录态、JavaScript 内存变量或桌面环境状态（如果本地执行环境发生重启，必须显式向模型反馈）。
  • 坐标映射与分辨率：截图上传建议采用 detail: "original" 配置；如果对图片进行了降采样缩放，必须将相对坐标重新等比映射回真实的物理视口像素。OpenAI 官方实测中表现最好的桌面分辨率为 1440×900 与 1600×900。
  • 高危操作闸口：字段 pending_safety_checks 与 acknowledged_safety_checks 依然承担着高危操作的安全放行机制，尽管目前该字段完整的 Schema 定义仅保留在 Azure 的旧版 OpenAI 文档中。
  • 支持动作全集：模型支持的底层动作类型涵盖 click（点击）、double_click（双击）、drag（拖拽）、keypress（按键）、move（移动鼠标）、screenshot（截屏）、scroll（滚动）、type（文本输入）以及 wait（等待）。

Anthropic：Claude Computer Use

Claude 将 Computer Use 交付为一套标准的客户端工具集（client toolset），其参数结构已直接固化在模型内部，开发者无法随意篡改或重新定义。目前最新的正式商用（GA）版本为 computer_toolset_20260801（早期版本 computer_20251124 仍予以保留），内部打包了 17 个子工具。

当前最新工具集支持 7 款模型：claude-fable-5-1、claude-mythos-5-1、claude-fable-5、claude-mythos-5、claude-opus-5、claude-sonnet-5 以及 claude-opus-4-8。

至于更早期的模型版本（如 Opus 4.7、Opus 4.6、Sonnet 4.6、Opus 4.5），严格来说并非不受支持，而是需要通过特定的 Beta 请求头调用旧版的 computer_20251124 工具。此外，从 Opus 4.7 开始，模型已支持长边达 2576 像素的高清视觉输入，这项优化的核心目的正是为了大幅降低 GUI 元素定位时的视觉坐标误差。

Anthropic 的核心架构取向非常明确：所有具体动作均在你自己的本地或沙箱环境中运行。 Anthropic 服务端本身不执行任何实际操作，模型仅负责输出 tool_use 数据块，而真正驱动屏幕、操作键鼠的职责完全交由你自己的执行框架（harness）来承担。

其坐标系采用标准的物理像素坐标：以屏幕左上角为原点 (0, 0)，X 轴向右递增，Y 轴向下递增。具体动作可以归纳为以下四大类：

# 屏幕观察与感知
screenshot              # 截取当前屏幕画面
cursor_position         # 查询鼠标指针当前坐标

# 鼠标指针操作
left_click / right_click / middle_click / double_click
mouse_move / drag

# 键盘输入
type                    # 键入文本
key                     # 触发快捷键或按键组合

# 滚动与缩放
scroll + direction + amount
zoom                    # 画面放大 / 缩小

在整套设计中，最容易踩坑的细节莫过于分辨率与坐标体系的处理：最新的 GA 工具集已不再接受屏幕物理尺寸参数（display-size parameters），模型输出的所有坐标，完全基于你刚刚回传给它的那张屏幕截图的像素空间。

这意味着，如果在向模型发送截图时做过缩放（降采样），客户端在实际执行点击前，必须手动将模型返回的坐标按比例放大还原回物理屏幕坐标，否则点击必然偏离目标位置。只有在旧版的 computer_20251124 工具集中，才需要在初始化时预先声明 display_width_px 和 display_height_px。

智能体的核心运行回路需要完全由开发者自行实现：向 API 发送包含 Computer 工具定义与用户任务指令的请求；Claude 会返回一个或多个 tool_use 数据块（支持批量打包多个动作）。

你的客户端执行框架按序逐一执行这些动作，并将每个工具的执行结果打包成 tool_result 回传（截取的屏幕截图以图像内容块格式上传）。

整个交互持续循环，直到模型返回 end_turn 结束本轮任务。

此外，思考深度可通过参数 output_config.effort 进行精细控制，同样提供 low / medium / high / xhigh / max 五个档位。

孪生能力：专为网页打造的 Browser Use

在面向桌面的 Computer 工具之外，Anthropic 于 2026 年 8 月正式商用了孪生工具集 Browser Use（browser_toolset_20260801）。它是专门针对浏览器场景构建的解决方案，内部打包了 31 个子工具，其中 27 个默认开启，4 个高权限工具需显式按需启用（file_upload 文件上传、javascript_exec JS 脚本执行、read_console 控制台日志读取、read_network 网络抓包）。

与 Computer Use 的纯像素感知不同，Browser Use 的感知通道以无障碍树（Accessibility Tree / AXTree）结合视口快照为主，不再单纯依赖原始图像像素；而在行动层面，其操作直接指向具体的元素引用句柄（例如 ref_4），而非物理像素坐标。Anthropic 官方产品文档明确指出：在纯网页自动化场景下，这才是首选推荐的最佳实践。

这一演进背后的工程意义极为深远：Anthropic 实际上早已在生产环境中落地了“无障碍树 + 元素句柄引用”的技术范式。“Claude 只会按像素绝对坐标点屏幕”也仅仅适用于桌面级交互场景，Anthropic 官方的产品技术路线图已明确表明，“结构化语义优先、纯视觉图像兜底”，才是整个自动化行业正在加速收敛的演进方向。

安全防御与隔离策略

在安全基线方面，Anthropic 官方建议将智能体部署在独立的虚拟机（VM）或容器中，遵循最小权限原则，严格隔离敏感凭据与数据，并配置域名白名单机制；同时，模型本身也在训练阶段针对提示词注入（Prompt Injection）做了专门的对抗强化。

这里有一个流传甚广的数据需要特别澄清：社区与行业中被频繁引用的“提示词注入攻击成功率从 23.6% 降至 11.2%”，其实并不出自 Computer Use 官方文档，而是来自浏览器插件 Claude for Chrome 在自主模式下经过红队攻防及缓解措施后的披露数据。

当前 Computer Use 的官方文档仅披露了一套分类器检测机制，系统会主动扫描截图中的潜在注入信号，并在命中时暂停操作、弹窗交由人工确认，但并未公开具体的量化防御指标。

然而，即便按照插件攻防披露的数字来看，“大约仍有九分之一的恶意注入能够成功穿透防线”，对于具有严重后果的高风险操作，人工介入确认依然是不可逾越的底线。

Google：Gemini Computer Use

  • 工具定位：工具名称为 computer_use。演进至 Gemini 3.x 世代后，它已成为一项原生内置工具，不再需要依赖专门的独立模型（此前版本则必须配合专用的 gemini-2.5-computer-use-preview 模型使用）。
  • 运行环境枚举：官方划分为三大目标环境，分别是网页浏览器、移动端与桌面端（对应枚举常量 ENVIRONMENT_BROWSER、MOBILE、DESKTOP）。
  • 执行方式：遵循标准的函数调用（Function Calling）范式，由客户端环境（例如 Playwright）具体承接并执行生成的动作指令。官方提供的参考实现直接配套了开箱即用的 Docker 沙箱。
  • 坐标体系：坐标统一归一化为 1000×1000 的相对网格，由客户端根据真实物理视口的宽高将其等比换算为物理像素，这与 Claude 采用的直接输出原始物理像素坐标形成了鲜明对比。
  • 动作指令集：包含 open_web_browser（打开浏览器）、click_at（指定坐标点击）、type_text_at（指定坐标输入）、navigate（跳转网址）、scroll_document / scroll_at（页面/局部滚动）、hover_at（悬停）、drag_and_drop（拖拽）、wait_5_seconds（等待 5 秒）、go_back / go_forward（后退/前进）、key_combination（组合快捷键）以及 search（搜索）。
  • 意图与安全透明度：模型的每次响应都会附带一个 intent 字段说明该步骤背后的意图与推理逻辑，并附带一个 safety_decision 判定结果（regular 正常执行 / require_confirmation 需人工确认 / blocked 拦截阻断），整个执行过程并非不可见的黑盒，你可以清晰获知模型为何在特定位置执行点击。
  • 运行交互闭环：向模型发送包含工具配置、环境类型、任务提示词与当前屏幕截图的请求 → 接收模型返回的 function_call、intent 和 safety_decision → 客户端执行该操作（或根据安全判定进行拦截） → 截取最新屏幕状态并附带当前 URL 作为 function_response 回传 → 重复上述循环直至任务完成。
  • 安全与策略控制：支持可配置的策略分类与覆盖规则，提供按需开启的截图注入检测能力，并在每一步操作上都通过上述三态 safety_decision 进行安全闸口校验（旧版由 ALLOWED / REQUIRES_CONFIRMATION 构成的二态方案现已废弃）。
  • 基准表现与调用成本：官方主要基于 2.5 预览版模型给出自测说明，在 WebArena 上取得领先、Online-Mind2Web 拥有高准确率，且在 Mobile Control 移动端控制场景下表现强劲，但暂未公布绝对基准评分；价格方面，预览版阶段每百万 tokens 约为输入 $1.25 / 输出 $1.25 至输入 $1.25 / 输出 $10 不等。值得注意的是，高频截屏所产生的多模态视觉 tokens 构成了最主要的成本开销，这也是所有纯视觉方案在落地时必然面临的共同挑战。

VLM 究竟是如何“看屏并点击”的？

三家大厂虽然产品形态各异，但底层依赖的核心思路基本一致：多模态大模型将屏幕截图编码为视觉 tokens，结合文本提示词指令与历史操作上下文展开联合推理。然而，这种看似简单的“看一眼就点”模式，背后其实隐藏着三个非常棘手的工程问题。

坐标定位精度才是真正的核心瓶颈。 从“看懂屏幕内容”到“精准点在这一像素上”，本质上已经不再是纯粹的语义理解问题，而是几何定位（Geometry）问题。输入的图像分辨率高低，直接决定了模型输出点击坐标的精度上限。以 Claude 为例，其截图长边上限从早期模型的 1568 像素（约 115 万像素）直接提升至 Opus 4.7 后的 2576 像素（约 375 万像素）；Anthropic 官方更新说明对此明确强调，此举正是为了从物理分辨率层面降低界面元素的定位误差（Grounding Error）（顺带澄清一下，以往社区常说的 1280×720 仅仅是早期的“推荐尺寸”，从来都不是硬性上限）。

各厂商的微调策略各有侧重。 OpenAI 在 CUA 时代采用明确的“SFT 监督微调 + RL 强化学习”两阶段训练体系；而现役的 Astra 则是结合强化学习、专门针对专业办公场景进行了深度定向优化的推理模型（OpenAI 尚未公开完整的训练管线）。Anthropic 则直接将工具 Schema 固化在底座模型内部，并针对提示词注入做专项防御微调。Google 则是先推出专用的独立预览模型，验证成熟后再将该能力合流沉淀为原生工具。三者路径各异，但底层技术押注完全一致：让模型吞吐足够多经过精准对齐的“截图-动作”数据。

视觉 tokens 是真正的吞金兽。 一张高分辨率截图塞入上下文窗口，就会瞬间消耗数千 tokens；而在运行回路的每次循环迭代中，这笔成本都会被重复扣除，操作步数越多、截图分辨率越高，调用账单就会越发飙升。Google 官方定价文档中明确将截图成本列为最主要的开销来源，这也正是所有基于纯视觉路线的智能体方案必然会有的问题。

纯像素 vs 元素引用 vs 混合模式

在 Computer Use 的系统设计中，真正的工程权衡本质上是像素与结构的选择。目前主流存在三种设计路径：

  • 基于物理像素坐标（Pixels）：模型直接输出具体的 (x, y) 坐标。这是三家厂商目前默认交付的纯视觉路径。它的优势在于 API 设计极其简洁、部署轻量通用；但劣势在于每一步都必须重新做视觉对齐（Visual Grounding），一旦页面发生响应式布局变动或样式调整，先前识别到的“固定位置”就会立即失效。
  • 基于元素引用句柄（Element References / Accessibility Tree）：模型输出类似 click(ref=e47) 的结构化指令，客户端将其解析并映射到具体的 DOM 节点。这种方式执行确定性高，且大幅节省视觉 token 开销；但致命弱点在于对 DOM 的动态突变极其脆弱，而且遇到缺乏标准 ARIA 无障碍属性的自定义组件时，往往会完全失灵。
  • 混合模式（Hybrid）：DOM 结构优先解析，纯视觉截图作为动态兜底。这正是当前生产环境正在迅速收敛演进的核心方向，值得单立章节深入拆解。

为什么无障碍树（AXTree）会成为网页生产环境的默认选择？ 核心原因在于信息密度的显著优势：原生无障碍树所包含的节点数量通常只有原始 DOM 树的极小一部分——业内估算大致在 1% 到 10% 之间，本文参考的资料显示约为 5% 到 10%。

反映到 token 开销上，解析整页无障碍树通常只需要几百到两千 tokens，而未经精简的原始 DOM 往往轻松突破 1.5 万（15K）tokens。这种精简不仅意味着调用成本成倍下降，更关键的是带来了清晰的语义信息（清晰标注了元素的 role 角色、name 名称、state 状态与 description 描述），大幅提升了操作的确定性。无论是 Playwright MCP、开源的 Browser-Use 还是官方的 Claude for Chrome，底层无一例外都采用了这套“AXTree 主导、屏幕截图兜底”的混合范式。

当然，该方案也有明显的边界与软肋：不符合 WCAG 无障碍规范的网页、采用 Shadow DOM 深度封装的组件、基于 Canvas 渲染的应用（如 Figma、Google Sheets、Canva），以及 CSS 层叠层级（z-order）造成的视觉遮挡，都会导致无障碍树提取出的数据失真或失效。

安全防御与环境隔离：行业通行的“三件套”

让 AI 直接接管真实屏幕，其安全风险远比单纯的代码执行要严峻得多：它可能直接触及你的真实浏览器、敏感账号以及本地文件。为了应对这些风险，目前行业已普遍形成了三层递进的标准防御体系：

环境沙箱化（Sandboxing）。 早期 OpenAI 的 CUA / Operator 采用云端托管的虚拟浏览器；现役的 Astra 则通过 ChatGPT Work / Codex 桌面端的权限受控接入，同时配合搭载独立用户数据隔离区、支持一键彻底重置清除的云端浏览器。Anthropic 服务端自身完全不执行任何动作，运行环境全由开发者自行提供独立的虚拟机或容器沙箱。Google 官方参考实现则直接内置了 Docker 沙箱方案，在生产级落地中推荐接入 Browserbase 等云端虚拟浏览器。

高危敏感操作的人工二次确认（Human-in-the-Loop）。 资金转账、消息发送、日程删除、账号登录以及验证码破解等敏感行为，通常都会强制触发人工介入。OpenAI 的接管模式（Takeover Mode，在人工接管操作期间系统会停止记录日志以保护隐私）、Anthropic 的高危操作人工确认机制，以及 Google 的 safety_decision 决策体系，本质上都是这一设计理念在不同技术栈下的具体实现。

提示词注入（Prompt Injection）的主动检测防御。 OpenAI 采用“实时注入监控（命中即暂停）+ 针对工具调用推理的异步安全审查（命中即暂停或直接终止会话）”的双重屏障；Anthropic 运行自动分类器实时扫描截图中潜藏的恶意注入特征，并在触发时弹窗提示人工确认（需要再次强调的是，前文提到常被引用的 23.6% → 11.2% 是 Claude for Chrome 浏览器插件红队攻防的实测数据，官方 Computer Use 文档本身已不再公开具体指标）；Google 则提供了可按需启用的截图注入检测功能，并结合每一步操作前置校验的 safety_decision 机制进行联合把关。

客观而言，一个不可回避的结论是：“环境沙箱 + 人工确认 + 注入检测”虽然已成为全行业的标准配置，但提示词注入防御至今仍难以做到万无一失，Anthropic 披露的大约九分之一穿透率便是最直接的明证。

因此，工程架构的正确设计目标，绝不是寄希望于构筑一堵“绝对无法被攻破的高墙”，而是设计一套深度防御体系，确保即便其中任意单层防线被攻破，也绝不会对用户的核心资产造成实质性损害。

生态版图：浏览器智能体与 GUI 定位基座模型

Computer Use 并非技术孤岛；在真实的工程实践中，还有两条紧密相邻的技术演进路径。

全系统桌面级 Computer Use（如 Claude 的桌面工具集、早期的 CUA、Gemini Desktop）追求极强的通用性，理论上能够操作任何软件的图形界面，但代价是执行较慢、调用成本高昂，且纯像素坐标在不同界面缩放下极易失效。相比之下，专精于浏览器的智能体（Browser Agents）（如 Browser-Use、Stagehand、Playwright MCP、Skyvern 等）在生产落地上表现得更加稳定可靠，因为绝大多数现代网页都能直接通过 DOM 或无障碍树（AXTree）选择器完成交互：元素定位确定性极高，同时大幅节省 token 开销。两者之间与其说是技术路线的竞争，不如说是通用性与执行效率之间的权衡取舍。目前工业界最主流的生产落地架构是混合模式，在网页端优先走 DOM / AXTree 结构化解析，只有当遭遇 Canvas 重度渲染的应用、强反爬机制目标或陈旧老式网站时，才回退到纯像素视觉方案。

专门的 GUI 定位基座模型（Grounding Models）则聚焦于一个更专一的细分环节：将自然语言指令（如“点击提交按钮”）直接映射为屏幕上的物理像素坐标。这类模型更倾向于作为模块即插即用地嵌入各类智能体框架中，而非承担端到端的全流程智能体角色：

  • UGround（俄亥俄州立大学团队出品，入选 ICLR 2025 Oral）：最初基于 LLaVA-NeXT（7B）构建，在 130 万张屏幕截图及 1000 万个网页元素上进行预训练。它完全依托纯视觉感知，不依赖任何 HTML DOM 或无障碍树信息，直接预测物理像素坐标。随后的 UGround-V1 迁移至 Qwen2-VL 底座，提供 2B / 7B / 72B 三种规格参数，在 ScreenSpot 基准上的定位准确率比此前 SOTA 提升了约 20 个绝对百分点。其配套框架 SeeAct-V 更是做到了职责分离：由通用多模态大模型（MLLM）负责整体任务规划，而底层具体的元素坐标定位则完全交由 UGround 处理。
  • ShowUI（2B）：一款轻量级 VLM 模型，仅依托 25.6 万条精简训练样本，就在 ScreenSpot 上取得了 75.1% 的零样本（Zero-shot）定位准确率；它通过视觉特征与动作流交替穿插（interleaved vision-action stream）的方式，显著提升了页面导航定位的连贯性。
  • OmniParser（微软出品）：一套屏幕解析工具包，能够精准检测屏幕中的可交互区域并自动生成图标的语义描述；通常与 GPT-4V / 4o 搭配实现视觉标记驱动（Set-of-Mark）的元素定位。在 ScreenSpot 基准评测中，它在桌面文本识别上取得 91.3 分，在桌面图标识别上取得 63.6 分。
  • OS-Atlas、Aguvis、UI-TARS：更大规模的 GUI 基座模型，专为攻克更高难度的基准测试（如 ScreenSpot-Pro）而设计，持续刷新着复杂界面的视觉定位上限。

这类模型的真正价值，在于与前沿厂商的大模型形成了极强的互补：将计算成本极高的元素定位环节，从昂贵的全能端到端大模型中剥离出来，交由以低成本合成数据训练的轻量化小模型专精解决。这与头部厂商闭源、大一统的端到端方案相比，构筑了一套截然不同的成本结构与工程演进思路。

综合对比与全局图景

在此必须开门见山说明一个前提：OSWorld 2.0 评测同时存在“二元判别（非对即错）”与“部分得分”两种计分机制，且该基准的维护团队曾明确指出，不同版本任务集之间的得分并不具备直接可比性。

例如 Astra 测得的 72.6% 与 Claude Opus 5 测得的 70.2%，均出自 OpenAI 官方发布的同一张对比表格（基于其 V2-Offline 子集测试）；而更早期的 Claude 基线成绩（基于 3.5 Sonnet 的纯截图方案，得分为 14.9% / 22.0%）则出自完全不同的渠道，即 Anthropic 官方的 Model Card 附录。

将它们并列放置主要是为了提供宏观的工程演进参照，并非严谨意义上的同口径横向排名。

总结

  1. 核心交互回路已高度收敛。 三家大厂的底层范式完全一致：获取截图/状态 → 多模态推理决策 → 输出结构化动作 → 客户端执行并重新捕获状态。真正的工程分水岭主要落在两个维度：感知通道（纯像素 vs. 混合感知）与动作空间表达（绝对坐标 vs. 元素引用句柄）。
  2. 纯像素方案已经不太够用。 基于物理坐标的纯视觉智能体虽然普适通用，但执行效率慢、调用成本高昂，且对分辨率和页面排版极其敏感。生产落地的重心正在加速转向“DOM / 无障碍树优先，视觉截图动态兜底”，就连 OpenAI 自身也已从早期的纯 CUA 范式，全面演进为如今“截图主导 + 代码执行 + 多工具混合”的务实路线。
  3. 视觉定位是核心瓶颈，也是挑战机遇。 UGround、ShowUI 以及 OmniParser 等工作，将“从自然语言映射到像素坐标”的定位任务，从昂贵的全能前沿基座大模型中解耦出来，借助低成本合成数据与专用轻量化小模型精准攻克，这为端到端闭源大模型之外，开辟出了一条极具竞争力的模块化工程替代路径。
  4. 安全问题仍然不可避免。 沙箱隔离、高危操作人工确认与注入检测已成为行业通用标配，但即便是 Anthropic 自身披露的数据，恶意注入也仍有大约九分之一的穿透率。因此工程上必须坚持“多层纵深防御、单层失效可控”的容错设计，绝不能寄托于某一道必须绝对完美防守的高墙。
  5. 终局正在加速走向多技术融合调度。 从最初的纯视觉 Computer Use，演进到“DOM 结构推理 + 视觉兜底 + 确定性校验”的混合体，再到如今“自主探索 → 编译为脚本 → 自我迭代优化”的闭环学习，AI 操作电脑正在逐步脱离单纯“模仿人类点击屏幕”的初级阶段，演进为一种兼具人类灵活性与自动化脚本确定性的全新系统级能力。
